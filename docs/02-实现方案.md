# 1. 关键设计决策

v1.0 中有几处设计在真实仓库上跑不通，v1.1 先把这些决策定下来，后文都以此为准。

| 问题 | v1.0 做法 | v1.1 决策 | 原因 |
|---|---|---|---|
| 评测测试可见性 | 默认 Agent 可以跑目标测试 | 推理阶段看不到评测测试，Agent 自己生成复现测试 | SWE-bench 的 FAIL_TO_PASS 测试是答案的一部分，推理时使用即为泄漏 |
| 沙箱网络 | 全程 `network=disabled` | 环境构建阶段联网，测试执行阶段断网 | 不联网无法 `pip install` |
| 依赖安装 | 每次运行时安装 | 按 `(repo, commit, env_spec)` 缓存镜像；SWE-bench 复用官方镜像构建逻辑 | 真实仓库安装一次要数分钟，且依赖版本问题是最大的不稳定来源 |
| Token 预算 | `max_tokens: 50000` | 默认 100 万 token；费用上限由用户按所选模型自行设定 | 一次带工具调用的修复通常需要几十万 token，5 万连一轮都不够 |
| 回归判定 | 全量测试 PASS | 与 base commit 的测试基线对比，只统计新增失败 | 真实仓库在 base commit 上通常就有失败或被跳过的测试 |
| 检索打分 | 原始分直接加权 | 先按通道归一化再加权，同时实现 RRF 作对照 | BM25、余弦相似度、图距离量纲不同，直接相加没有意义 |
| Patch 格式 | 未定义 | search/replace 块为主，unified diff 为备选 | LLM 直接写 unified diff 时行号和上下文经常出错 |
| 存储 | PostgreSQL + Redis 必选 | SQLite 默认，PostgreSQL / Redis 可选 | 单机评测不需要，减少环境搭建成本 |
| 测试确定性 | 未定义 | FakeLLM + 录制回放 | Agent 逻辑必须能在不调用真实 LLM 的情况下测试 |

# 5. LLM 调用层

## 5.1 接口

```python
class LLMRequest(BaseModel):
    messages: list[Message]
    tools: list[ToolSpec] | None = None
    response_schema: type[BaseModel] | None = None
    temperature: float = 0.0
    max_output_tokens: int = 4096
    purpose: str                 # "plan" / "code" / "diagnose" ...，用于统计

class LLMResponse(BaseModel):
    content: str | None
    tool_calls: list[ToolCall]
    parsed: BaseModel | None
    input_tokens: int
    output_tokens: int
    cost: float                  # 已换算为 budget_currency
    model_alias: str
    latency_ms: int

class LLMProvider(Protocol):
    async def complete(self, request: LLMRequest) -> LLMResponse: ...
```

实现：

- `OpenAICompatibleProvider`：base_url、model、api_key 都来自配置，一个实现覆盖所有兼容 OpenAI Chat Completions 协议的服务（见「多 Provider 接入」）；
- `FakeLLM`：按预置脚本依次返回响应，脚本耗尽时抛异常，测试中用来精确控制 Agent 行为；
- `RecordingLLM(inner)`：包装真实 provider，把请求和响应写入 `llm_calls.jsonl`；
- `ReplayLLM(path)`：按请求内容的 hash 返回录制结果，找不到时抛 `ReplayMissError`，不静默调用真实接口。

## 5.2 结构化输出

```text
schema → JSON Schema 写入 prompt（支持时同时开启 provider 的 JSON 模式）
       → 解析 JSON
       → Pydantic 校验
       → 失败：把校验错误附在消息末尾重试，最多 2 次
       → 仍失败：抛 StructuredOutputError，由节点决定降级或终止
```

内部状态只保存校验通过的对象，不保存自由文本。

## 5.3 多 Provider 接入

V1 要支持 DeepSeek、Kimi（Moonshot）、GLM（智谱），并保留 OpenAI 及其他兼容服务。这几家都提供 OpenAI 兼容接口，所以不为每家单独写 SDK 适配，只用 `OpenAICompatibleProvider` + 配置区分。

配置示例（`configs/llm.yaml`，密钥只通过环境变量引用）：

```yaml
providers:
  deepseek:
    base_url: https://api.deepseek.com
    api_key_env: DEEPSEEK_API_KEY
  kimi:
    base_url: https://api.moonshot.cn/v1
    api_key_env: MOONSHOT_API_KEY
  glm:
    base_url: https://open.bigmodel.cn/api/paas/v4
    api_key_env: ZHIPU_API_KEY

models:
  # key 是项目内的模型别名；model 字段填各家官方文档中的模型 ID
  deepseek-chat:
    provider: deepseek
    model: <官方模型 ID>
    context_window: 128000
    supports_tools: true
    supports_json_mode: true
    supports_temperature: true
    price: {currency: CNY, input_per_mtok: <单价>, output_per_mtok: <单价>, cached_input_per_mtok: <单价>}
  kimi-main:
    provider: kimi
    model: <官方模型 ID>
    ...
  glm-main:
    provider: glm
    model: <官方模型 ID>
    ...

roles:            # 每个 Agent 角色使用哪个模型别名
  issue_analyzer: deepseek-chat
  localizer: deepseek-chat
  planner: deepseek-chat
  coder: deepseek-chat
  reproducer: deepseek-chat
  diagnoser: deepseek-chat
  reviewer: deepseek-chat
  failure_classifier: deepseek-chat   # 只在规则分类未命中时调用
```

base_url、模型 ID、上下文长度、单价都以各家官方文档为准，并且会变化，所以只放在配置里，代码中不出现任何具体模型名。上面的 base_url 是编写时的公开地址，接入时要再核对一次。

### 能力差异处理

各家兼容程度不完全一致，差异通过模型配置中的能力字段处理，不在业务代码里写 `if provider == "glm"`：

| 差异 | 处理方式 |
|---|---|
| 不支持原生 tool calling（部分推理模型） | `supports_tools: false` 时改用 prompt 内的 JSON 工具调用协议：模型输出 `{"tool": ..., "arguments": ...}`，由结构化输出流程解析和重试 |
| 不支持 JSON 模式 | 只在 prompt 中给 JSON Schema，靠 Pydantic 校验 + 重试保证格式 |
| 不支持 / 忽略 temperature | `supports_temperature: false` 时不发送该参数 |
| 上下文长度不同 | Context Builder 的预算取 `min(角色预算, context_window × 0.75)` |
| 推理模型返回思考内容 | 思考内容单独存入 `llm_calls.jsonl`，不放回下一轮对话、不进入 RepairState |
| tool_call 参数是非法 JSON | 视为一次结构化输出失败，带错误信息重试 |
| 错误码和限流方式不同 | 统一映射成 `RateLimitError` / `ProviderError` / `ContextTooLongError`，`ContextTooLongError` 触发 Context Builder 按 50% 预算重建一次 |

### 兼容性测试

- 单元测试：用 `httpx.MockTransport` 模拟各家响应格式差异（tool_calls 结构、usage 字段、错误体），不访问网络；
- 冒烟测试（`@pytest.mark.llm`，默认不跑）：对每个已配置的模型发送同一组请求（普通对话、结构化输出、一次工具调用），结果写入 `artifacts/llm_smoke/`；新增或更换模型前必须先通过。

### 数据外发

使用云端 API 时，Issue 文本和仓库代码片段会发送给对应服务商。处理私有仓库前需要确认这是允许的。配置中可以设 `allowed_providers` 白名单，未列出的 provider 拒绝调用。

## 5.4 成本与限流

- 每次调用按该模型配置的单价计算费用，累加到 `RepairState.usage`；有缓存命中计价的模型按缓存价计算命中部分；
- 不同模型的币种可能不同，统一按配置中的汇率换算为 `budget_currency`（默认 CNY）后再累加和比较预算；
- 429 / 5xx 指数退避重试 3 次，重试不计入 Agent 迭代次数，但计入费用；
- 每个 provider 有独立的并发上限（`max_concurrency`），benchmark 并行跑任务时不会超过服务商的限流；
- 每个节点进入前检查预算，超出时直接路由到 `finalize`。

## 5.5 可复现性

LLM 输出即使 `temperature=0` 也不保证确定。可复现性分两层：

- 过程可复现：录制的 `llm_calls.jsonl` 可以通过 `ReplayLLM` 完整重放一次运行，用于调试和 Dashboard 回放；
- 结果统计可复现：benchmark 每组配置跑多个 seed，报告均值和置信区间，见「统计方法」。

# 6. Repository 获取与 Workspace 隔离

```text
repo_url + base_commit
   ↓
cache/repos/<repo_hash>/          # bare clone，多个任务共享，只读
   ↓  git worktree add / 复制
runs/<run_id>/workspace/          # 每次运行独立，Agent 只能改这里
```

- 用户提供的本地路径同样先复制到 workspace，原目录不被修改；
- workspace 创建后执行 `git status --porcelain` 确认干净；
- Agent 的每次编辑都在 workspace 中进行，候选 patch 用 `git diff base_commit` 导出；
- 回退到 base 用 `git checkout -- . && git clean -fd`，只作用于 workspace；
- 运行结束后 workspace 默认保留 7 天用于排查，可配置立即删除。

# 7. Repository Index

## 7.1 数据模型

```python
class FileNode(BaseModel):
    id: str
    repository_id: str
    path: str                    # 相对仓库根目录，统一使用 "/"
    module: str | None           # 如 "auth.service"
    size: int
    sha256: str
    line_count: int
    is_test: bool
    parse_error: str | None

class Symbol(BaseModel):
    id: str                      # sha1(repository_id + qualified_name + kind)
    file_id: str
    name: str
    qualified_name: str
    kind: Literal["module", "class", "function", "method", "test_function", "test_method"]
    start_line: int
    end_line: int
    signature: str | None
    docstring: str | None
    decorators: list[str]
    parent_id: str | None

class GraphEdge(BaseModel):
    source_id: str
    target_id: str | None        # 无法解析时为空
    target_name: str             # 原始名字，保留用于 lexical 匹配
    kind: Literal["CALL", "IMPORT", "INHERIT", "REFERENCE", "TEST"]
    confidence: Literal["high", "medium", "low"]
    line: int
```

## 7.2 Qualified name 规则

- 模块名由文件路径推导：去掉 `src/` 前缀（若存在 `src` layout），去掉 `.py`，`/` 换成 `.`，`__init__.py` 对应包名；
- 类内方法：`module.Class.method`；
- 嵌套函数：`module.outer.<locals>.inner`；
- 同名重复定义（如条件定义）：保留全部，追加 `#2`、`#3` 后缀。

## 7.3 解析范围

Tree-sitter 节点：`function_definition`、`class_definition`、`decorated_definition`、`call`、`import_statement`、`import_from_statement`、`argument_list`（基类）、`expression_statement` 中的首个 string（docstring）。

V1 不做数据流分析和类型推断。

## 7.4 调用边解析

按顺序尝试，命中即停：

| 情形 | 示例 | 解析方式 | confidence |
|---|---|---|---|
| 同模块函数 | `helper()` | 当前模块的顶层 symbol | high |
| 导入的名字 | `from x import f` 后 `f()` | 沿 import 表找到目标 symbol | high |
| 模块属性 | `import x` 后 `x.f()` | 模块 symbol 表 | high |
| `self.method()` | | 当前类及仓库内基类的方法 | medium |
| `ClassName(...)` | | 类的 `__init__` | medium |
| `obj.method()` | 类型未知 | 仓库内所有同名方法，各连一条边 | low |
| 其他 | | 只记录 `target_name` | low（target_id 为空） |

同名方法超过 5 个时不展开，只记录名字，避免 `get()`、`run()` 这类名字把图连成一团。

## 7.5 Test 关联

一个测试关联到目标 symbol 的依据，按强度排列：

1. 测试函数体内直接调用了该 symbol（high）；
2. 测试文件 import 了该 symbol 所在模块，且测试名包含 symbol 名（medium）；
3. 文件命名约定：`tests/test_service.py` ↔ `service.py`（low）。

V1 不做覆盖率驱动的关联。V2 可以在 base commit 上用 `coverage.py` 动态收集测试到函数的映射，精度会明显更高，但需要先能跑通全量测试。

## 7.6 Git history

- 只读取 base commit 的祖先提交（`git log base_commit`），不读取之后的提交，否则会把修复本身泄漏进来；
- 记录每个文件最近 N 次（默认 200 次提交范围内）的修改次数，以及最近一次修改距 base 的提交数；
- symbol 级修改频率：对每次提交的 diff hunk 行范围，映射到 base commit 上同文件的 symbol 范围，近似即可。

## 7.7 增量索引

以 `(repository_id, path, sha256)` 判断文件是否变化。只重新解析变化的文件，然后删除并重建与这些文件相关的边。

# 8. Retrieval

## 8.1 Query 构造

从 Issue 文本中抽取：

| 类型 | 抽取方式 | 用途 |
|---|---|---|
| traceback 帧 | 正则 `File "(.+)", line (\d+), in (\w+)` | 直接映射到仓库内文件与 symbol，作为强种子 |
| 代码标识符 | 反引号内容、`a.b.c` 形式、驼峰 / 下划线词 | 精确匹配 |
| 异常与错误信息 | `XxxError: ...`、引号中的报错文本 | 在源码中搜索 raise / 字符串常量 |
| 文件路径 | `foo/bar.py` 形式 | 直接匹配 |
| 自然语言关键词 | 分词 + 停用词过滤 | BM25 |

标识符拆分：`getUserName` → `get user name`，`user_id` → `user id`，同时保留原词。

## 8.2 各通道

所有通道的检索单位都是 symbol（函数 / 方法 / 类）。模块级代码作为一个 `module` symbol。

| 通道 | 输入 | 原始分 |
|---|---|---|
| lexical | 标识符 + 关键词 | BM25 分；ripgrep 精确命中 symbol 名或错误字符串时额外加分 |
| semantic | Issue 全文 embedding | 与 symbol 文档的余弦相似度 |
| structural | lexical / semantic Top-20 作为种子 | 沿 CALL / INHERIT / IMPORT 扩展，深度 d 处的分数 = 种子分 × 0.5^d，最大深度 2 |
| test | Issue 中提到的测试名、traceback 中的测试帧 | 通过 TEST 边反推被测 symbol |
| history | 无 | 文件近期修改次数的 log 归一化 |

Symbol 文档格式（用于 BM25 和 embedding）：

```text
path: auth/service.py
symbol: auth.service.UserService.login
signature: def login(self, token: str) -> User
docstring: ...
code: <函数体，超过 60 行时截断为前 40 行 + 后 10 行>
```

## 8.3 归一化与融合

每个通道先在本次查询的候选集内归一化，再加权：

```python
def min_max(scores: dict[str, float]) -> dict[str, float]:
    if not scores:
        return {}
    lo, hi = min(scores.values()), max(scores.values())
    if hi == lo:
        return {k: 1.0 for k in scores}
    return {k: (v - lo) / (hi - lo) for k, v in scores.items()}

def weighted_fusion(channels: dict[str, dict[str, float]],
                    weights: dict[str, float]) -> dict[str, float]:
    fused: dict[str, float] = defaultdict(float)
    for name, scores in channels.items():
        for sid, s in min_max(scores).items():
            fused[sid] += weights[name] * s
    return dict(fused)

def rrf(rankings: dict[str, list[str]], k: int = 60) -> dict[str, float]:
    fused: dict[str, float] = defaultdict(float)
    for ranked in rankings.values():
        for rank, sid in enumerate(ranked, start=1):
            fused[sid] += 1.0 / (k + rank)
    return dict(fused)
```

默认权重：semantic 0.30、lexical 0.20、structural 0.20、test 0.15、history 0.15。这组数字只是起点，Phase 2 在检索评估集上对比加权融合和 RRF，选更好的作为默认。为避免在评测集上调参造成过拟合，调参只在 synthetic 集和单独划出的 SWE-bench 开发子集上进行，不在报告用的测试子集上进行。

traceback 中直接出现的仓库内 symbol 不参与融合，固定排在最前。

## 8.4 文件级聚合

文件分 = 该文件内 symbol 融合分的最大值 + 0.1 × 其余 Top-3 symbol 分之和。同时报告文件级和函数级 Recall@K。

## 10.1 Issue Analyzer

```python
class IssueAnalysis(BaseModel):
```

## 10.2 Localizer

两步，均为只读：

1. 文件级：给 LLM 看检索 Top-15 文件的骨架和检索分，选出 ≤3 个文件并说明理由；
2. Symbol 级：给 LLM 看选中文件的骨架和 Top symbol 的源码，选出 ≤5 个 symbol，每个附行范围和理由。

```python
class LocalizationResult(BaseModel):
    files: list[RankedFile]
    symbols: list[RankedSymbol]      # 含 start_line / end_line / reason
    retrieval_snapshot_id: str        # 指向完整检索结果，用于事后分析
```

## 10.3 Impact Analyzer

纯规则，不调用 LLM：

- callers / callees 取图上深度 1；
- tests 取 TEST 边 + 同目录测试文件；
- 风险：

| 条件 | 风险 |
|---|---|
| 只改私有函数（`_` 开头）或函数内部逻辑，签名不变 | LOW |
| 改公开函数且调用者 > 5，或修改类的公开方法 | MEDIUM |
| 改函数签名、`__init__.py` 导出、基类方法（有子类覆盖） | HIGH |

风险等级影响 Review 的严格程度和回归测试的范围，不阻止修改。

## 10.4 Planner

只读工具：`read_file`、`search_code`、`find_symbol`、`get_callers`、`get_callees`、`get_related_tests`。

```python
class PlannedChange(BaseModel):
    file: str
    symbol: str | None
    action: Literal["modify", "add", "delete"]
    description: str

class RepairPlan(BaseModel):
    root_cause_hypothesis: str
    evidence: list[str]
    changes: list[PlannedChange]
    tests_to_run: list[str]
    planned_new_tests: list[str] = []   # 打算新增、尚未存在的测试（不是可执行目标）
    risk: Literal["low", "medium", "high"]
    alternatives: list[str]          # 如果当前方案失败，下一步可以尝试的方向
```

### 10.4.1 计划的两阶段校验（Harness Hardening 追加）

形状与语义是两件事，必须分开校验、且都要在同一个**有界**纠正环里：

| 层 | 判据 | 失败后 |
|---|---|---|
| Schema | `RepairPlan` 的 Pydantic 校验 | 带字段路径回灌，模型重试 |
| 语义 / 权限 | 见下 | 同上；预算耗尽写 `plan_rejected`，归因 `plan_semantic_invalid`（模型侧），**不**写 `workflow_error` |

`tests_to_run` 只接受**已存在且被授权执行**的测试文件路径或 pytest NodeID：路径必须
落在 workspace 内、不在拒绝名单（含隐藏评测目录）里、是测试形态、`::` 后的每一段
函数/类名必须真的出现在文件里。它会被送进 Sandbox 真的执行，所以"打算写的测试"写在
这里是错的。

`planned_new_tests` 表达新增测试意图。它**永远不是**可执行目标；能否写进交付补丁仍由
`WorkspacePathPolicy.allow_new_tests`（DA-009 可信配置）与 diff 层的
`new_tests_reviewed` 决定，计划本身不授予任何权限。已有测试文件受保护：不能计划改写
或删除。若 `planned_new_tests` 非空而 `tests_to_run` 为空，计划被拒——新测试不能单独
作为修复成功的证据。

`planned:` / `todo:` 这类模型自造的前缀标记一律判为非法意图，**不**剥掉前缀继续校验：
剥掉之后 `tests/test_ledger.py::test_new` 仍会因"函数不存在"被拒，说明它本来就不是
可执行目标。

## 10.5 Reproduction Agent

- 输入：Issue 分析、定位结果、相关已有测试的源码（作为写法参考）；
- 输出：`tests/_codepilot_repro/test_repro.py`；
- 校验：在 base commit 的 sandbox 中运行，必须 FAIL，且失败原因与 Issue 描述相关（失败类型是 AssertionError 或 Issue 中提到的异常类型；`ImportError`、`SyntaxError` 不算有效复现）；
- 复现测试只用于 Agent 内部判断，最终 patch 中剔除。
- 计数规则：1 次初始尝试 + 最多 3 次重试，`attempts ≤ 4`、`retries = attempts - 1`，`attempts` 只能由校验循环真实累加（schema 强制它等于历史条目数）。
- `ENV_ERROR` / `SANDBOX_ERROR` / `WORKSPACE_ERROR` 是独立状态，立即短路，不消耗 LLM 重试预算；重试耗尽后状态为 `failed` 并降级使用仓库已有测试，复现失败不终止后续修复流程。
- 失败类型取自 JUnit 结构化字段（`type` 属性 → traceback 末行 `file:line: ExcName` → message 前缀），不在 stdout 里搜字符串；pytest 的 `Failed: DID NOT RAISE X` 属断言族失败，按 AssertionError 处理，只有 X 确实出现在 Issue 文本里才升级为「Issue 点名异常」。
- **「base 上有效失败」不等于「问题已复现」**：前者是本模块能证明的判据（配合候选必须触达定位文件、静态拒绝伪复现），后者需要评测侧确认同一测试在 gold patch 上 PASS（Phase 6 D-08）。

## 10.6 Patch Reviewer

只读。输入 Issue、Plan、diff、目标测试结果、回归结果、Impact 风险。

```python
class ReviewResult(BaseModel):
    approved: bool
    risk: Literal["low", "medium", "high"]
    issues: list[ReviewIssue]        # 每条含 severity、file、line、description
    summary: str
```

Reviewer 也是 LLM，它的判断可能与测试结论冲突。规则：测试未通过时不调用 Reviewer；测试通过、Reviewer 拒绝时，只有 severity=high 的问题会触发一次额外修复，否则按通过处理并在 Report 中记录意见。这样可以避免 Reviewer 无休止地挑剔。

# 11. Coding Agent 与工具

## 11.1 工具清单

| 工具 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `read_file` | path, start_line?, end_line? | 带行号的内容 | 单次最多 400 行 |
| `search_code` | pattern, regex?, path_glob? | 匹配列表（最多 50 条） | ripgrep |
| `find_symbol` | name | symbol 列表 | 支持模糊匹配 |
| `get_callers` / `get_callees` | qualified_name | symbol 列表 + confidence | |
| `get_related_tests` | qualified_name | 测试列表 | |
| `edit_file` | path, search, replace | 成功 / 失败 + 最相近片段 | 主编辑方式 |
| `create_file` | path, content | 成功 / 失败 | 只能在仓库内 |
| `get_git_diff` | 无 | 当前 diff | |

所有路径参数先做 `resolve()`，必须位于 workspace 内，拒绝 `..`、绝对路径和符号链接逃逸。工具不提供任意 shell。

## 11.2 Patch 格式

主格式是 search/replace：

```text
path: auth/service.py
<<<<<<< SEARCH
    user_id = payload["user_id"]
=======
    user_id = payload.get("user_id")
    if user_id is None:
        raise AuthenticationError("token missing user_id")
>>>>>>> REPLACE
```

应用规则：

1. 精确匹配，且必须唯一；
2. 精确匹配失败时，忽略行尾空白再匹配；
3. 仍失败时，返回文件中与 search 块相似度最高的 3 段（difflib），让 Agent 重新提交；
4. 匹配到多处时返回错误和所有位置，要求 Agent 扩大 search 块。

unified diff 作为备选格式，用 `git apply --check` 先校验再应用。

## 11.3 循环控制

每轮 Coding Agent 最多 30 次工具调用。到达上限或调用 `finish` 时结束本轮，进入 Patch Validator。

`run_tests` 只能运行 workspace 中已有的测试和复现测试。在 SWE-bench 模式下，评测用的 `test_patch` 从未进入 workspace，所以 Agent 无法通过这个工具接触评测测试。

# 12. Patch Validator

按顺序检查，任一项失败即拒绝并把原因返回给 Coding Agent（计入迭代次数）：

| 检查 | 规则 |
|---|---|
| 路径 | 所有改动文件位于 workspace 内；不改 `.git/`、`.github/`、`setup.cfg`、`pyproject.toml`、`tox.ini`、`pytest.ini`、`conftest.py`（可配置） |
| 规模 | 改动文件数 ≤ `max_files_changed`；增删行数 ≤ `max_lines_changed` |
| 语法 | 所有改动的 `.py` 文件 `ast.parse` 通过 |
| 非空 | diff 不为空，且不只是空白或注释变化 |
| 测试保护 | 已有测试文件（`is_test=True`）不允许修改，除非配置 `allow_test_edits=true` |
| 作弊模式 | 见下表 |

作弊模式检测（基于 diff 的 AST 对比，不靠字符串匹配）：

| 模式 | 检测方法 |
|---|---|
| 删除测试 | 修改前存在的 `test_*` 函数在修改后消失 |
| 跳过测试 | 新增 `pytest.mark.skip` / `skipif` / `xfail` 装饰器，或新增 `pytest.skip()` 调用 |
| 削弱断言 | 测试函数中 `assert` 语句数量减少，或断言被改为常量真值 |
| 吞异常 | 被修改函数中新增 `except Exception: pass` 或 `except: pass` |
| 硬编码期望值 | 被修改的非测试函数中新增的字符串 / 数字常量，同时出现在相关测试的断言中（启发式，命中时标记给 Reviewer，而不是直接拒绝） |
| 环境探测 | 新增对 `PYTEST_CURRENT_TEST`、`sys.modules["pytest"]` 等的判断 |

## 12.1 复现测试的唯一例外（Phase 6）

`tests/_codepilot_repro/` 是 Reproduction Agent 的专用目录，规则只有三条：

1. **写入需要可信凭证**：`WorkspacePathPolicy(repro_write=True)` 由运行装配方构造，不是模型可以设置的参数，因此 Coding Agent 即使给出这个路径也写不进去。有凭证时也只接受 `tests/_codepilot_repro/test_*.py` 这一层——`conftest.py`、`__init__.py`、嵌套目录、伪造目录名、大小写变体、`..`、symlink 一律拒绝。目录边界走 realpath 逐段比较，不是 `startswith()`。
2. **交付补丁里剔除它**：`generate_git_diff` 默认按目录前缀剔除复现文件，所以 Search/Replace、Unified Diff、`create_file` 与工具循环四种来源同时生效；修改文件数与行数统计随之干净，剔除项记录在 `CanonicalDiff.excluded_files` 里可审计。只有复现文件发生变化时，交付补丁为空并被「非空」检查拒绝——复现文件本身不构成一次修复。
3. **不改用户的 `.gitignore`**：忽略语义只在本项目的 diff 生成层实现。工作树里仍然能 `git status` 到复现文件，Agent 读取与执行它不受影响，非复现文件的追踪也不受影响。

如果 Issue 本身就要求修改测试（例如“这个测试写错了”），需要在任务配置中显式设置 `allow_test_edits=true`，并由 Reviewer 复核。

# 14. Failure 处理

## 14.1 流水线

```text
junit.xml + stdout/stderr
  → Failure Parser（每个失败测试一条 ParsedFailure）
  → Traceback 解析（区分仓库帧 / 第三方帧）
  → Failure Classifier（规则优先）
  → FailureSignature（用于重复检测）
  → Compressor（去重、截断、控制 token）
  → Diagnosis Agent（LLM，带证据）
```

## 14.2 ParsedFailure

```python
class TraceFrame(BaseModel):
    file: str
    line: int
    function: str
    in_repo: bool
    code: str | None

class ParsedFailure(BaseModel):
    test_id: str
    exception_type: str | None
    message: str
    frames: list[TraceFrame]
    deepest_repo_frame: TraceFrame | None
    category: FailureCategory
```

## 14.3 Failure Classifier

```python
class FailureCategory(StrEnum):
    SYNTAX = "syntax"                  # SyntaxError / IndentationError
    IMPORT = "import"                  # ImportError / ModuleNotFoundError（仓库内模块）
    NAME_ATTRIBUTE = "name_attribute"  # NameError / AttributeError
    TYPE = "type"                      # TypeError（参数个数、类型不匹配）
    VALUE_KEY_INDEX = "value_key_index"  # ValueError / KeyError / IndexError
    ASSERTION = "assertion"            # AssertionError，测试断言不满足
    EXPECTED_EXCEPTION_MISSING = "expected_exception_missing"  # pytest.raises 未触发
    TIMEOUT = "timeout"
    COLLECTION = "collection"          # 收集阶段失败
    FIXTURE = "fixture"                # fixture 初始化 / 清理失败
    ENVIRONMENT = "environment"        # 第三方依赖缺失等，不由 patch 引起
    UNKNOWN = "unknown"
```

规则：先看 junit 的 `type` 属性，再看 traceback 最后一行的异常类型，最后匹配 `DID NOT RAISE` 等 pytest 特有文本。规则命中率在 Phase 7 的样本集上统计，`UNKNOWN` 才调用 LLM 分类。

## 14.4 FailureSignature

```python
def failure_signature(f: ParsedFailure) -> str:
    frame = f.deepest_repo_frame
    location = f"{frame.file}:{frame.function}" if frame else "no_repo_frame"
    message = normalize(f.message)   # 去掉 0x 地址、数字、临时路径、引号内长字符串
    return sha1(f"{f.exception_type}|{location}|{message}")
```

一轮执行的签名是该轮所有失败签名排序后的集合。

## 14.5 Compressor

- 同一签名的多个失败只保留 1 个完整样本，其余只列测试名；
- 每个失败只保留仓库内帧，以及第三方帧中的最后一帧；
- message 超过 2000 字符截断；
- 总量超过诊断预算时，按“目标测试 > 复现测试 > 新增回归 > 其他”的优先级保留。

## 14.6 Diagnosis

```python
class Diagnosis(BaseModel):
    failure_category: FailureCategory
    root_cause: str
    evidence: list[Evidence]         # 每条含 kind（traceback / code / test）、file、line、text
    suspected_symbols: list[str]
    is_patch_caused: bool            # 失败是本轮 patch 引入的，还是原问题未修复
    repair_strategy: Literal["refine", "revert_and_retry", "expand_scope", "give_up"]
    confidence: float
```

校验：evidence 中的 `file:line` 必须在 workspace 中存在，不存在的条目删除，并按删除比例降低 confidence。`confidence` 只用于日志和分析，不用于控制流程，因为 LLM 自报的置信度没有校准。

## 15.1 RepairState

使用 Pydantic 模型（而不是 TypedDict），保证序列化和校验：

```python
class Usage(BaseModel):
    input_tokens: int = 0
    output_tokens: int = 0
    cost: float = 0.0                       # budget_currency
    llm_calls: int = 0
    by_model: dict[str, ModelUsage] = {}    # 按模型别名分别统计

    diagnosis: Diagnosis | None

class RepairState(BaseModel):
    task_id: str

    # ---- 局部额度与补丁身份（Phase 11；语义见 §15.3 与 §15.5）----
    coding_stop_reason: StopReason | None = None  # 编码阶段自己的局部停止原因
    frozen_patch_hash: str = ""                   # 编码阶段交出去的补丁 SHA-256
    review_calls: int = 0                         # 真正执行过的审查次数（专属额度）
    review_skip_reason: str | None = None         # 审查未执行的原因
    closure_admission: ClosureAdmission | None = None  # 闭环测试额度准入读数（Phase 12）

    budget: RepairBudget
    usage: Usage = Usage()
    test_runs: int = 0
    started_at: datetime
    status: Literal["running", "succeeded", "failed", "stopped", "error"] = "running"
    stop_reason: StopReason | None = None
```

`coding_stop_reason` 与 `stop_reason` 是两件事，刻意分成两个字段：前者只说明
“这一轮编码不能再改代码了”，**不**等于任务结束；后者才是这次运行结不结束。把两者
写成一层会让编码阶段的局部额度把补丁校验、目标测试与独立审查一起跳过（Phase 11
的缺陷根因，见 `docs/notes/phase11-closure-budget.md`）。

`closure_admission` 是**读数不是记账**（Phase 12，§15.3.3）：它记录派发前“闭环还要几次
测试执行 / 当时还剩几次 / 编码阶段被允许自己跑几次”，从不写入 `usage` 或任何计数器，
所以重放与跨进程恢复都不会因为它多花一次容器或多记一笔费用。`None` 只出现在没走完整
闭环图的运行里（Phase 5 单次图），**不等于**“额度充足”。

`ReviewResult.reviewed_patch_hash` 由 `review` 节点盖章（不是模型自报），用于回答
“这条结论审的是哪一版补丁”。补丁换了版本，旧结论不得给新补丁背书。

大字段（完整日志、完整检索结果）不放在 state 中，只存 artifact 路径。

## 15.2 节点与路由

```text
START
 → understand_issue
 → retrieve
 → localize
 → analyze_impact
 → build_env              # 构建或命中环境镜像，生成 baseline
 → reproduce              # 生成并验证复现测试（失败则跳过，记录原因）
 → plan
 → generate_patch
 → validate_patch
     ├─ invalid → check_budget
     └─ valid   → run_target_tests
 → run_target_tests
     ├─ PASS → run_regression
     ├─ FAIL / TIMEOUT / COLLECTION_ERROR → diagnose
     └─ ENV_ERROR / SANDBOX_ERROR → finalize
 → run_regression
     ├─ 无新增失败 → review
     └─ 有新增失败 → diagnose
 → review
     ├─ approved 或无 high 问题 → finalize(succeeded)
     └─ 有 high 问题且未复审过 → check_budget
 → diagnose → check_budget
 → check_budget
     ├─ 任一停止条件满足 → finalize(stopped)
     └─ 否则 → repair_patch
 → repair_patch → validate_patch
 → finalize → END
```

“目标测试”的定义：有复现测试时是复现测试；否则是 Planner 选出的已有相关测试；都没有时直接进入回归。

每个节点签名都是 `async def node(state: RepairState, deps: Deps) -> dict`，返回要更新的字段。`Deps` 通过闭包注入（LLM、sandbox、index、event sink），节点内部不读取全局对象。

### 15.2.1 闭环转移与局部额度（Phase 11）

`generate_patch` / `repair_patch` 里的编码循环撞到**局部**额度（每轮工具调用上限、本局
token/费用天花板）时，转移只看“手上有没有补丁”：

- **有补丁**：冻结该版本的 SHA-256 写进 `frozen_patch_hash`，把局部原因写进
  `coding_stop_reason`，**不写 `status`**。图继续走 `validate_patch → run_target_tests →
  run_regression → review`。局部额度只说明“不能再改代码了”，不说明“不需要验证了”。
- **没有补丁**：这才是终态，失败原因如实写 `EMPTY_PATCH`，验证与审查无从谈起。
- 被 PatchValidator 拒绝的补丁不进成功收尾：`validate_patch → check_budget`，
  `finalize` 判 `patch_rejected`。
- 校验器发现候选补丁与冻结身份不一致时，把不一致写进失败原因，不悄悄替换。

`repair_patch` 的入口在既有预算守卫之后再加一道**闭环准入**（Phase 12，§15.3.3）：剩余
测试次数撑不起下一版候选的闭环时，这一轮**不启动**，直接写
`status=budget_exhausted` + `stop_reason=budget_closure_test_runs`。顺序是有意的：
准入判定排在“清空回归与审查结论”那一步**之前**，所以被拒的轮次不会把上一轮已经挣到的
证据一起带走——报告里那一版补丁仍然是“验过、审过、绑定自己哈希”的，缺的只是被故意拒绝的
下一轮（`unexecuted_stages` 追加 `repair_round:<trigger>:…`）。

`review` 节点三条硬规矩：前置条件（`review_preconditions()`，`routing` 与
`PatchReviewer` 共用同一实现）不满足时**不调用模型**并把原因写进 `review_skip_reason`；
结论盖上被审补丁的 SHA-256；同一版补丁的重放复用已有结论，不重复调用模型、不重复计
`review_calls`、不重复记账。`finalize` 只接受“审查结论绑定当前候选补丁”的成功，
未执行、过期或绑定其他补丁的结论一律不算验证通过。

判定顺序本身也是契约：**先判同版重放能否复用，再判前置条件，最后才判额度**。把额度
检查放在最前面，会让已经审过的同一版补丁在次数用满后被拦在门外，也会让一次“没钱所以
没发请求”的审查在 Operation Journal 里留下一条没有结果的意图行（下次重进直接判
“结果不确定”）。被额度拦下时同样要写 `review_skip_reason`
（`not executed: <stop_reason> spent before any call`）：`review_executed=False` 只说
“没审”，说不出是没接 Reviewer、前置条件不成立，还是没钱/没次数。

## 15.3 RepairBudget

```python
class RepairBudget(BaseModel):
    max_iterations: int = 5              # repair_patch 最多执行次数
    max_test_runs: int = 12              # 含目标测试、回归、复现验证
    max_files_changed: int = 5
    max_lines_changed: int = 150
    max_tool_calls_per_iteration: int = 30
    max_review_calls: int = 2            # review 节点自己的专属额度（初审 + 一次复审）
    max_runtime_seconds: int = 1800
    max_total_tokens: int = 1_000_000
    max_cost: float | None = None        # 单任务费用上限，单位为 budget_currency；None 表示不限
    budget_currency: str = "CNY"
```

单任务费用上限没有固定默认值：不同模型单价差别很大，同一个数字换个模型含义就完全不同。用户在 `configs/*.yaml` 或命令行 `--max-cost` 中自行设定。未设定时仍受 `max_total_tokens` 和 `max_runtime_seconds` 约束，不会无限运行；benchmark 运行前打印按 token 上限和当前模型单价推算的单任务费用上界，供用户确认。

`max_test_runs` 与 v1.0 相比从 8 提高到 12，因为一次完整流程至少包括：复现验证 1 次、目标测试每轮 1 次、回归 1–2 次。默认值在 Phase 10 根据实际分布调整，调整结果写入实验报告。

### 15.3.1 四类预算的分工与专属额度（Phase 11）

| 预算 | 上限 | 计数口径 | 拦住谁 | 作用域 |
|---|---|---|---|---|
| 工具调用 | `max_tool_calls_per_iteration=30` | `state.tool_calls`（只由编码节点整体覆盖） | 当前这一轮的编码循环 | **局部** |
| 修复迭代 | `max_iterations=5` | `len(attempts) - 1`（首轮 `generate_patch` 不计入） | `repair_patch` 派发 | 局部 |
| 模型调用与费用 | `max_total_tokens`、`max_cost` | `state.usage` 累计绝对值 + 派发层已预扣未结算的费用 | 每个节点入口 + 编码循环内每一圈 + 闭环预留（覆盖所有排在审查之前的模型调用） | 全局 |
| 验证与审查 | `max_test_runs=12`、`max_review_calls=2` | `state.test_runs`、`state.review_calls` | 测试节点入口、`review` 节点、**修复轮的闭环准入（§15.3.3）** | 专属 |

`max_review_calls` 与 `max_tool_calls_per_iteration` **互不相干**：Coder 烧光本轮 30 次工具
调用不能占用审查的额度，否则编码阶段会把独立审查一起冻结（首次真实运行就是这个形状：
`stop_reason=budget_tool_calls`、Reviewer 从未执行，而补丁其实是对的）。计数走
`state.review_calls`，中断恢复时从 checkpoint 读回，同一版补丁的重放复用结论不计数。

### 15.3.2 闭环预留（`BudgetManager.closure_reservation`）

排在审查之前的模型调用，必须把“校验 → 目标测试 → 回归 → 审查（→ 有界修复 → 复审）”
要花的额度先留出来。预留**不是记账**：从不写入 `state.usage`，因此不可能重复计费；它只
把 `RESERVATION_BEARING_ACTIVITIES = {LLM, CODEGEN, REPAIR}` 的可用上限压低，验证与审查
作为受益方仍用真实硬上限。

- **作用域**：`Activity.LLM` 也在清单里，这是本轮的实质修正。第一版只收紧
  `CODEGEN`/`REPAIR`，于是 `diagnose`（以及 `understand_issue` / `retrieve` / `localize`
  / `analyze_impact` / `plan` / `reproduce`）这些同样排在审查之前的调用可以随意支配留给
  审查的钱——现象与“被编码烧光”一模一样：`review` 入口真的没钱了，只能如实记未执行。
  实现落在**统一预算准入**上（节点入口的 `BudgetManager.evaluate`），不给任何节点各配
  一套算法；`CodingAgent` 额外拿到净去预留后的循环内天花板。
- **次数**：按状态机算“**还欠几次审查**”（`routing.pending_review_calls`）：当前候选补丁
  还没审过时初审 1 次、`review_repairs < 1` 时再算 1 次复审；结论已经绑定当前候选且没有
  high 时 0 次；`review_calls` 已到 `max_review_calls`、或 run 已进终态时 0 次。结果受剩余
  专属额度封顶。**预留随闭环状态收敛**，不会因为“曾经欠着审查”而永久占用预算。
- **token**：每次审查按 `REVIEW_CONTEXT_TOKENS(24_000) + REVIEW_OUTPUT_TOKENS(4_096)`
  计，与 `agents/reviewer.py` 用的是同一份常数（改一处不会漂移）；观测到的“平均每调用
  token”更大时取更大者。
- **可用额度的口径**：判定用 `上限 - 已结算费用 - 派发层已预扣未结算的费用 - 闭环预留`。
  预扣来自进程级逐请求账本（`llm/dispatch_budget.py`），由装配层注入
  `Deps.outstanding_cost`；它是“已经承诺出去、`state.usage` 还没看见”的钱，漏算就会在
  一笔并不存在的余额上再扣一次预留。币种与预算不一致又缺汇率时，这笔钱当作**未知**
  （`convert()` 缺汇率按 1.0 处理会把七倍差额读成“差不多”），由 fail-closed 分支处理。
- **费用**：**优先**按 Reviewer 实际绑定模型的单价估算 ——
  `LLMConfig.resolve_role("reviewer")` → `ModelPrice` 的输入价/输出价（缓存价刻意
  **不折价**，预留要担保最坏情况）→ `llm.cost.compute_cost` 换算到 `budget_currency`。
  单价缺失、不完备，或币种与预算不一致且缺汇率时，退回账本实测单价
  `state.usage.cost / state.usage.total_tokens`；两者都不成立时 `estimated=false`。
  口径（`reviewer-model:<别名>` / `observed-unit` / `simulated-zero-cost` / `unknown` /
  `no-reviewer` / `review-not-pending`）写进预算事件与阻断消息，事后能看出该核对哪份
  单价配置。
  账本平均单价只代表“已经跑过的调用”，在编码与审查用不同模型时**不是**保守值，因此
  只作回退。
- **fail closed**：费用估不出来且设了 `max_cost` 时，把剩余额度全部视作预留，派发在花钱
  之前就被 `budget_cost` 拦下 —— 未知费用不得当成零。反过来 0 token / 0 费用是合法读数
  （FakeLLM 与免费额度就这么记账），不得当成“估不出来”。预留作用域扩到第一个 LLM 节点
  之后这条边界会以新形态复发：**账本为空**发生在 run 的第一个节点上，把“还没调用过”读成
  “估不出来”会让每个模拟批次在 `understand_issue` 就被拦住（实测形态
  `SMOKE_COMPLETED_NO_PATCH`）。收口口径是按**费用来源**判断，而不是按调用计数：
  `cost_unknown_calls > 0` 才是下界、必须拦；模拟 provider（`simulated_llm=true`）没有
  货币费用，账本为空时是“已知的 0”；真付费 provider 拿不到任何价格依据时照旧 fail closed。

预留作用在两个点：派发前判定（不足则阻断派发，一个请求都不发）与循环内判定
（净去预留后的 `token_ceiling` / `cost_ceiling` 传给 `CodingAgent.run()`，每圈都判）。
测试次数与迭代次数不进预留：它们已分别在测试节点入口与 `check_budget` 判定，不足时
补丁留在“未验证”状态并被如实报告，不会被伪造成通过。

**同一笔调用只记一次账**。`state.usage` 是预留与所有预算判定的读数来源，因此
"补一层统计层"的判据必须按**账本对象**查重：
`llm/tracking.py:tracks_usage(provider, usage)` 沿 `inner` 逐层看有没有任何一层在往同一个
`Usage` 记。按最外层的 `isinstance` 判断会被装饰器骗过 —— 冒烟链路把每个角色 provider
包进 `--temperature` / `--max-output-tokens` 覆盖层，`PatchReviewer` 于是套上第二层，
真实运行里表现为"账本 26 次 vs 派发账本 25 次 HTTP"、事件流两条 `llm_call`。重复记账
不只是报表难看：它让预算判定看到一笔并不存在的支出，闭环额度因此少一份。

### 15.3.3 闭环测试额度准入（`BudgetManager.closure_test_plan`，Phase 12 / DA-024）

token/费用预留管不住第三次真实单题运行（glm14）暴露的缺口：那一次只花了 ¥0.192 / ¥10 硬上限，
把运行判死的是 **测试次数**。两轮“目标测试 + L2 + L3”加上基线两次与编码阶段自己调用的
`run_tests` 就花满了 `max_test_runs=12`，于是第二轮候选的 L3 被拦在测试节点入口
（`regression.complete=false`），审查从未执行。

测试次数**不能**像 token 那样按比例预留：它是离散次数，而且编码阶段的 `run_tests` 与闭环的
目标测试、回归**共用同一个计数器**（`AccountingSandbox` 数的就是这些调用）。所以这里做两件
事，作用点都在**派发之前**：

- **准入**：`required = 补丁校验 0 次 + 目标测试（有才计 1 次）+ 当前配置要求的回归层级
  （L2 / L3 各 1 次；L3 已被 `MAX_FULL_REGRESSION_RUNS` 判不再跑时不计）`。
  `剩余 < required` 时修复轮**不启动**：`status=budget_exhausted`、
  `stop_reason=budget_closure_test_runs`，不回退 Workspace、不重新规划、不派发编码。
  已经审过的补丁、审查留下的 high 问题与回归结论**原样保留**（清空那些字段发生在这道判定
  之后），因此绝不产出“注定无法完成验证”的新候选补丁。
- **份额**：可行时把编码阶段本轮可以自己调用的 `run_tests` 压到
  `coder_share = 剩余 - required - flaky 复跑预留(2)`（不为负），由
  `CodingAgent.run(test_run_ceiling=…)` 在循环内执行：超出份额的 `run_tests` 请求被工具层
  以 `closure_reserved` 原样回话给模型（其余工具照常可用），因此被限制的是“模型再自己验
  一遍”，不是“这一版补丁不被验证”。不变量：`coder_share + required ≤ 剩余`。

三条口径边界：

- **计数按调用、不按用例**：真实基线里 L3 一次圈进 779 条也只算一次。写成用例数会让准入
  在任何真实仓库上都永远不足。
- **flaky 复跑预留不参与准入**：它只在真的出现疑似新失败时发生；把它算进 `required` 会把
  “本来能走完闭环的一轮”判成不可行。而它拿不到额度时的后果是既有的安全降级
  （`complete=false` → 审查记未执行），不会被读成通过。
- **抽样不是省额度的手段**：`regression_mode=sampled` 与 `full` 都是同一次调用。额度不足时
  唯一正确的动作是**不启动那一轮**，而不是把 FULL 降成 SAMPLED、跳过必要测试、跳过审查或
  降低成功判定。`max_test_runs` 的默认值同样**不因单次现象上调**：glm14 的形状是“12 次对
  单轮闭环 + 基线仍够用，只是被编码阶段借走了 2 次”，准入与份额修正之后同样的两轮
  （8 次真实需求）就能正常收口。

判定读数是可审计的：`state.closure_admission`（`schemas/budget.py:ClosureAdmission`）记录
`runs_spent / allowance / required / 各层级 / retry_reserve / coder_share / trigger / feasible
/ detail`，同一句算式同时出现在 `events.jsonl` 的 `budget_check`、`failure_reasons` 与
`RunReport.closure`；`feasible=false` 时 `unexecuted_stages` 追加
`repair_round:<trigger>:…`，报告 markdown 写 `REFUSED before dispatch`。它是**读数不是记账**：
从不写入 `state.usage` 或计数器，因此重放与跨进程恢复同一条边既不多花容器也不多计费。

## 15.4 进度判定

```python
class ProgressSnapshot(BaseModel):
    target_failed: int
    regression_new_failures: int
    signatures: frozenset[str]

def made_progress(prev: ProgressSnapshot, cur: ProgressSnapshot) -> bool:
    if cur.target_failed < prev.target_failed:
        return True
    if cur.regression_new_failures < prev.regression_new_failures:
        return True
    # 失败数没变但失败签名变了，说明错误从一处推进到了另一处
    if cur.target_failed == prev.target_failed and cur.signatures != prev.signatures:
        return True
    return False
```

签名变化算作进展，是因为“先报 ImportError，修完后报 AssertionError”通常意味着修复在推进。但这也可能在两个错误之间来回振荡，所以同时检查：当前签名集合如果曾在更早的任一轮出现过，判为无进展。

## 15.5 停止规则

| stop_reason | 条件 |
|---|---|
| `budget_iterations` / `budget_test_runs` / `budget_tokens` / `budget_cost` / `budget_time` | 对应预算耗尽 |
| `budget_tool_calls` | 本轮编码循环用满 `max_tool_calls_per_iteration`。**局部**：有补丁时只记进 `coding_stop_reason`，图继续走验证与审查；只有没有补丁才成为终态 |
| `budget_review_calls` | 审查专属额度 `max_review_calls` 用尽。与 `budget_tool_calls` 分开：前者是“审查轮次用完”，后者是“编码没工具调用了”，混成一个原因就看不出是谁饿死了谁 |
| `budget_closure_test_runs` | **闭环准入**（§15.3.3）：剩余测试次数撑不起下一版候选的闭环，于是修复轮在启动之前被拒。留在 `budget_*` 家族里是为了让既有的归因分桶（`TaskOutcome.over_budget`、SWE-bench 的 `BUDGET_STOPPED`）继续把它算成预算停止，而不是掉进“补丁无效/模型没修好”；值本身与 `budget_test_runs` 区分：前者是“还剩 2 次而闭环要 3 次”（派发前的算术），后者是“12 次已经花完”（运行结果），修法完全不同 |
| `repeated_patch` | 本轮 patch hash 与历史任一轮相同 |
| `repeated_failure` | 连续 2 轮失败签名集合完全相同 |
| `no_progress` | 连续 2 轮 `made_progress` 为 False |
| `sandbox_failure` | `SANDBOX_ERROR` 或 `ENV_ERROR` |
| `validation_loop` | 连续 3 次 patch 校验失败 |
| `diagnosis_give_up` | Diagnosis 给出 `give_up` |

判定优先级固定（`graph/budget.py::_PRIORITY`）：迭代 → 测试次数 → 工具调用 → 审查调用
→ token → 费用 → 墙钟。顺序固定的意义在于 `stop_reason` 必须可复现，同一状态两次判定
给出同一个原因，路径测试才能断言。边界口径：**已用 ≥ 上限即视为耗尽**。

patch hash 只归一化 diff 里**不含内容**的 git 元数据（`index <sha>..<sha>`、`--- a/`、`+++ b/`、
CRLF），并把 `\ No newline at end of file` 转成显式标记参与哈希；正文行逐字保留。

不能写成"去掉所有空白差异"：Python 的缩进是语法，三引号字符串行尾的空格也是数据，
抹掉全部空白会让两份语义不同的补丁得到同一个 hash，`repeated_patch` 于是在错误的
时间点停止修复（也可能反过来放过真正重复的补丁）。代价是"只差一个行尾空格"的两份
补丁被判为不同、多花一轮预算——漏判重复只是多修一轮，误判重复会漏修，取向前者。
实现与被测试的负控制见 `graph/stop_rules.py` 与 `tests/unit/graph/test_stop_rules.py`。

## 15.6 修复策略

| Diagnosis 策略 | 行为 |
|---|---|
| `refine` | 在当前 patch 基础上继续修改 |
| `revert_and_retry` | workspace 回退到 base，带着全部失败历史重新生成，并提示 Planner 的 `alternatives` |
| `expand_scope` | 重新执行 symbol 级定位，加入诊断指出的 symbol，再生成 |

`is_patch_caused=True` 且连续两轮 `refine` 无进展时，强制切换为 `revert_and_retry`。

## 15.7 Checkpoint 与恢复

使用 LangGraph 的 SQLite checkpointer，`thread_id = run_id`。每个节点结束后自动保存。恢复时从最后一个完成的节点继续。sandbox 执行是幂等的（同一 patch 结果可以从 artifact 读取），所以重复执行不会造成副作用。

`recursion_limit` 设为 `20 + max_iterations × 6`，作为路由逻辑出错时的最后防线。

### 15.7.1 Benchmark 的节点级接入与恢复边界（Harness Hardening 追加）

`codepilot bench` 默认接上同一套 SQLite checkpointer（`--checkpoint/--no-checkpoint`）：
每个 (task, seed) 一份 `runs/<run_id>/checkpoints.sqlite`，`thread_id = run_id`。
任务级续跑（`ResultJournal`）与节点级恢复是两层不同能力——journal 只记得"哪些任务已经
有结论"，接不上"一张图跑到一半"的状态。续跑时 `BenchmarkRunner` 从 `manifest.json`
继承原 `run_id`（配置指纹不一致时拒绝继承），恢复进程按 run 目录里的
`workspace_identity.json` 认回 workspace 与索引的 `repository_id`，而不是重新推导。

上一段"sandbox 执行是幂等的，所以重复执行不会造成副作用"这句话需要限定：

- **不宣称 exactly-once**。崩溃落在"外部副作用已完成、checkpoint 尚未写入"的窗口时，
  那一轮会重做并重新计费；承诺的是 at-most-once-with-verified-evidence。
- 崩溃落在 Phase 9 Operation Journal 的"意图已写入、结果未提交"窗口时，恢复**拒绝**
  继续（写 `resume refused`），因为那次外部操作的状态本身就是不确定的，重放等于假装
  知道它没跑过。
- workspace 不存在、base commit 不符、补丁哈希与 checkpoint 不一致、artifact 缺失或
  摘要被改动，都拒绝复用证据并重新执行或安全终止。

## 15.8 自验证闭环的报告口径（Phase 11）

三份结论**各记各的**，任何一份都不得替代另一份：

| 记什么 | 字段 | 由谁决定 |
|---|---|---|
| Agent 内部的逐阶段真相 | `RunReport.closure`（`VerificationClosure`） | 本次运行的 state 与落盘证据 |
| Agent 内部的验证级别 | `report.verification_level(state)` → `m2_verified` / `sampled_verified` / `provisionally_verified` / `unverified` / 终态名 | 同一份闭环证据（单函数，装配层与报告同源） |
| 对外的问题是否解决 | `TaskRecord.resolved` / `evaluation_status`（官方 `RESOLVED` 等） | 外部官方 SWE-bench Harness |

`VerificationClosure` 逐条回答：补丁是否存在与其 SHA-256、是否由编码阶段冻结、
`coding_stop_reason`、Validator 是否执行及结果、目标测试是否执行与状态及其补丁身份、
回归是否执行/是否完整/L1-L2-L3 层级/新增失败数、Reviewer 是否执行/结论/未解决 high
数/结论是否绑定当前候选、是否发生审查后修复、审查额度用量、七类预算读数、硬费用上限
是否触顶、**闭环测试额度准入读数 `closure_admission`**（`runs_spent` / `allowance` /
`required` / `coder_share` / `trigger` / `feasible` / `detail`，Phase 12 §15.3.3），以及
**未执行阶段清单**。准入被拒时清单里必须出现 `repair_round:<trigger>:…`——被故意拒绝的
阶段同样是“未执行”，不能留白让人自己补成“大概做了”。

写报告的三条规矩：

- 未执行的阶段写成 `NOT EXECUTED`，不写成 `False`（`False` 会被读成“跑了，失败了”）。
- `m2_verified` 除了要求 `status == succeeded`，还要求审查结论**绑定当前候选补丁**；
  `reviewed_patch_hash` 为空按“未盖章”处理。
- 官方判分既不抬高也不降低内部级别；两者不一致时按既有机制记录差异
  （`compare_with_internal_m2` / `INTERNAL_NOT_CLAIM_OFFICIAL_RESOLVED`），不互相改写。

`results.jsonl` 每行同步带 `verification_level` / `review_executed` /
`review_bound_to_candidate` / `review_high_issues` / `post_review_repair` /
`unexecuted_stages` / `coding_stop_reason`，使逐题记录不必打开报告就能区分
“官方没判”“内部没审”“审了但不是这一版补丁”。恢复路径从 run 现场 manifest 读回这些
字段，避免把“已经审过”写成“从未执行”。

# 16. Regression 判定

## 16.1 三级测试

| 级别 | 范围 | 运行时机 |
|---|---|---|
| L1 目标 | 复现测试 / Planner 选出的相关测试 | 每轮 |
| L2 影响 | Impact Analyzer 给出的 tests + 被改文件同目录的测试 | L1 通过后 |
| L3 全量 | 仓库全部测试（预计耗时超出剩余墙钟时改为固定 seed 抽样 20%，记 `regression_mode=sampled`） | L2 通过后，每次运行最多 `MAX_FULL_REGRESSION_RUNS=2` 次 |

## 16.2 判定规则

```python
def new_failures(baseline: TestBaseline, after: ExecutionResult) -> list[str]:
    result = []
    for t in after.tests:
        before = baseline.outcomes.get(t.node_id)
        if before == "passed" and t.outcome in ("failed", "error") and t.node_id not in baseline.flaky:
            result.append(t.node_id)
    return result
```

- base 上本来就失败的测试，patch 后仍失败，不算回归；
- base 上不存在的测试（新增的复现测试）不参与回归统计；
- 新出现的失败重跑 2 次，任意一次通过就标记为 flaky，不计入回归，但在 Report 中列出。

## 16.3 降级

L3 的预计耗时（按 baseline 的总时长估算）超过剩余时间预算时，改为运行 L2 + 从剩余测试中按固定 seed 随机抽取 20%，Report 中标注 `regression_mode=sampled`。Benchmark 的正式结果以官方评测为准，不受此降级影响。

# 17. 评测

## 17.1 评测协议与信息隔离

推理阶段（Agent 可见）：

- Issue 文本（SWE-bench 的 `problem_statement`）；
- 仓库在 base commit 的完整内容；
- base commit 之前的 git 历史；
- 仓库中已有的测试。

推理阶段不可见：

- gold patch；
- 评测用的测试修改（`test_patch`）；
- FAIL_TO_PASS / PASS_TO_PASS 测试列表；
- base commit 之后的任何提交；
- SWE-bench 的 `hints_text`（默认不可见，可作为单独实验条件）。

实现方式：`SWEBenchLoader` 加载数据后立即拆成 `InferenceTask`（只含可见字段）和 `EvaluationTask`（只含评测字段）两个对象，分别交给推理模块和评测模块。推理模块的代码中不 import 评测模块，有一个测试用 import 检查保证这一点。

## 17.2 指标定义

记 N 为任务总数，所有比率的分母都是 N（包括环境构建失败的任务），环境失败另外单独报告：

| 指标 | 定义 |
|---|---|
| File Recall@K | gold patch 修改的文件中至少有一个出现在 Top-K 文件中的任务比例 |
| Function Recall@K | 同上，函数级；gold patch 只改模块级代码时，以模块 symbol 计 |
| Localization Exact@K | gold patch 修改的全部文件都出现在 Top-K 中的比例 |
| Resolved Rate | 最终 patch 通过评测（目标测试全部通过且 PASS_TO_PASS 无失败）的比例；SWE-bench 以官方 harness 为准 |
| First Attempt Resolved | 只取第一轮 patch 进行评测的通过比例 |
| Repair Gain | Resolved Rate − First Attempt Resolved |
| Repair Success Rate | 第一轮 patch 未通过的任务中，最终通过的比例 |
| Self-verified Precision | Agent 自认为成功的任务中，评测确认通过的比例。用来衡量复现测试和自检的可靠性 |
| Empty / Invalid Patch Rate | 没有产出有效 patch 的比例 |
| Iterations | 平均值、中位数、P90 |
| Cost | 每任务平均 token、费用、墙钟耗时；以及每解决一个任务的平均费用 |
| Stop Reason 分布 | 各 stop_reason 的任务数 |

Recall 的 gold location 由 gold patch 计算，只在评测阶段使用。

### 17.2.1 归因与两套解决率（Harness Hardening 追加）

"runner 跑完了"、"Agent 执行完了"、"补丁被独立评测判定了"是三层不同的事。把它们压成
一层会产生最难纠正的误读：一次 Harness 崩溃被记成 `resolved=false`，读者以为测的是模型
修复能力。因此每条 (task, seed) 观测除 `execution_state` 外还带两个维度：

- `evaluation_state ∈ {evaluated, not_run, error}`：独立评测到底发生了没有；
- `attribution ∈ {resolved, model_not_resolved, model_invalid_plan, model_output_error, harness_error, sandbox_error, env_error, budget_stopped, evaluation_not_run, evaluation_error}`。

配套指标（分母都写在自己身上，不共用）：

| 指标 | 分母 | 用途 |
|---|---|---|
| End-to-end Resolved | 全部派发（含未评测、崩溃、超预算） | "这批任务里有多少真的被修好了" |
| Conditional Resolved | 拿到独立评测判定的任务 | 唯一可作为模型能力读数的一项，必须与覆盖率同框出现 |
| Evaluation Coverage | 全部派发 | 条件读数的可信度 |
| Harness / Env / Sandbox Error Rate | 全部派发，三者分开 | 基础设施可靠性；`harness_error` **不等于** `env_error`，也不等于模型修复失败 |
| Model Plan Rejection / Output Error Rate | 全部派发 | 模型侧输出质量 |

上表原有的 Resolved Rate / First Attempt Resolved / Repair Gain 等定义与分母口径**保持
不变**：归因不通过排除任务来改善任何比率，端到端分母始终是全部派发。空补丁不再做独立
评测（拿它跑 gold 套件测的是坏掉的基线，不是模型的补丁），其 `resolved` 记为
`None`（未判定）而不是 `False`。

`results.jsonl` 自 v2 起带上述字段；Phase 10 的 v1 产物只在读取时做显式映射，不回写、
不重算历史数字。


First Attempt Resolved 需要对第一轮 patch 单独跑一次评测，所以每个任务保存每一轮的 patch。

## 17.3 Benchmark 数据格式（synthetic）

```text
benchmarks/synthetic/<task_id>/
├── repo/                   # 处于 bug 状态的仓库（含已有测试）
├── issue.md                # 只描述现象，不包含修复方法
├── env.yaml                # EnvSpec
├── eval/
│   ├── gold.patch
│   ├── test.patch          # 评测用测试，推理时不可见
│   └── tests.json          # {"fail_to_pass": [...], "pass_to_pass": [...]}
└── metadata.json           # category、难度、是否多文件、issue 是否含 traceback
```

结构与 SWE-bench 对齐，两者可以共用同一套评测代码。`eval/` 目录在推理时不会被复制进 workspace。

类别：wrong condition、missing validation、wrong exception、off-by-one、incorrect return、API misuse、edge case、cross-module dependency、regression bug、state / mutation bug。

synthetic fixture 由人工编写，LLM 可以辅助生成初稿，但每个 fixture 都要通过校验脚本，并人工确认 issue 描述没有泄漏答案。合成集的作用是开发调试和回归测试，不作为主要实验结论的来源。

## 17.4 SWE-bench 运行规模

| 步骤 | 规模 | 目的 |
|---|---|---|
| 冒烟 | 1 题 | 跑通全流程 |
| 开发子集 | 30 题（固定列表） | 调参、调 prompt，只在这里调 |
| 测试子集 | 50 题（固定列表，与开发子集不重叠） | 消融和主要结论 |
| 全量 | Lite 300 题 | 预算允许时运行，与公开榜单对比 |

费用估算：先在开发子集上跑 10 题，得到每题平均费用 c，全量消融费用约为 `c × 题数 × 组数 × seed 数`，在运行前写进实验计划。`codepilot bench` 支持 `--max-total-cost` 整批上限，达到后停止派发新任务，已完成的结果保留。

换模型会改变结果。主要实验固定一个模型；如果要比较 DeepSeek / Kimi / GLM，把“模型”作为单独的实验变量，在同一子集、同一配置下各跑一遍，不和组件消融混在一起。

SWE-bench 环境构建需要较大磁盘空间（官方镜像全量可达数百 GB），先按子集只构建用到的镜像。Windows 上需要在 WSL2 中给 Docker 分配足够磁盘和内存。

## 17.5 统计方法

- synthetic：每组配置 3 个 seed（通过不同的 temperature 采样或不同的 seed 参数），报告均值 ± 标准差；
- 组间对比：同一批任务上的配对 bootstrap（10000 次重采样），给出成功率差值的 95% 置信区间；区间包含 0 时报告为“未观察到显著差异”；
- 50 题规模下，成功率差异小于约 10 个百分点时通常无法得出显著结论，报告中要说明样本量限制。

## 17.6 消融

每组只改变一个配置项，配置文件见 `configs/ablation/`：

| 组 | retrieval | graph | iterative | diagnosis | reproduction | review |
|---|---|---|---|---|---|---|
| A | none | off | off | off | off | off |
| B | bm25 | off | off | off | off | off |
| C | bm25 + semantic | off | off | off | off | off |
| D | all | on | off | off | off | off |
| E | all | on | on（原始日志） | off | off | off |
| F | all | on | on | on | off | off |
| G | all | on | on | on | on | on |

A 组的 Agent 仍然可以使用 `search_code`、`read_file` 等工具，只是没有预先注入检索结果。这样衡量的是“检索作为先验”的价值，而不是“有没有工具”。


事件类型：`node_start`、`node_end`、`llm_call`、`tool_call`、`sandbox_run`、`budget_check`、`stop`。事件里不写 API key 和环境变量的值，写入前统一经过脱敏函数（匹配常见 key 格式）。

# 20. 测试策略

| 层级 | 内容 | 依赖 |
|---|---|---|
| unit | 解析、打分、融合、归一化、签名、校验、指标计算 | 无 |
| integration | 索引 fixture 仓库、检索评估、Context Builder | 无 |
| graph | 用 FakeLLM + FakeSandbox 覆盖所有路由路径和停止条件 | 无 |
| docker | Sandbox 资源限制、超时、网络隔离、残留清理 | Docker |
| e2e | 用 ReplayLLM 回放录制好的真实运行，断言结果不变 | Docker |
| llm | 真实 LLM 冒烟测试，默认不运行 | API key |

`FakeSandbox` 根据预置规则返回 `ExecutionResult`（例如“diff 中包含某字符串时 PASS”），让图测试不依赖 Docker。

覆盖率目标：`repo/`、`retrieval/`、`patch/`、`failure/`、`graph/`、`eval/` 行覆盖率 ≥ 80%；`agents/` 中的 prompt 模板不计入。

# 21. 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 环境构建失败 | 真实仓库无法运行测试，闭环无从谈起 | SWE-bench 复用官方镜像逻辑；用户仓库要求提供 EnvSpec；ENV_ERROR 单独统计 |
| 复现测试质量差 | 复现测试写错时，Agent 会“修好”一个错的目标 | 统计 Self-verified Precision；复现测试必须在 base 上以相关原因失败 |
| LLM 成本超支 | 消融实验跑不完 | 先估算再跑；固定子集；用户设定 `max_cost` 单任务上限和 `--max-total-cost` 整批上限 |
| 结果不可复现 | 结论不可信 | 多 seed + 置信区间；保存全部 llm_calls |
| 调参过拟合测试集 | 报告结果偏高 | 开发子集与测试子集分离 |
| 数据污染 | 模型可能在训练中见过 SWE-bench 的修复 | 在报告中说明；synthetic 集作为未污染的对照 |
| Windows 环境差异 | 路径、换行、Docker 行为不同 | 路径统一用 `pathlib` 和 posix 形式存储；git 设置 `core.autocrlf=false`（只作用于 workspace）；CI 在 Linux 上跑 |
| 工作量超出 | 后期阶段完成不了 | 按 04 中的降级顺序裁剪，核心闭环不裁 |
