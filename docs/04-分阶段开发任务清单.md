# CodePilot-Repair 分阶段开发任务清单

> 版本：v1.1  
> 阶段编号以本文件为准，01 / 02 / 03 中提到的 Phase 均指本文件的编号。  
> 使用方法：按 Phase 顺序交给 Coding Agent（Codex / Claude Code）。每个 Phase 同时满足“通用完成标准”和本阶段“验收”后，才进入下一阶段。

# 通用完成标准（每个 Phase 都适用）

- `uv run pytest` 通过，新增代码有对应测试；
- `uv run ruff check .`、`uv run mypy src` 无错误；
- 不依赖真实 LLM 的测试一律使用 FakeLLM 或录制回放（见 02「LLM 调用层」）；
- 需要真实 LLM 的验收写成脚本保存在 `scripts/`，可重复执行，运行产物保存在 `artifacts/`；
- 需要 Docker 的测试标记为 `@pytest.mark.docker`，Docker 不可用时自动 skip，并在汇报中说明；
- 文档同步更新；
- 汇报格式遵循 03-AGENTS.md §33，未实际执行的命令不得写 PASS。

# Phase 0：工程骨架 + LLM 调用层

## 目标

可运行、可测试的 Python 工程，后续所有模块都依赖的基础设施在这一阶段一次定好：配置、状态模型、LLM 抽象、事件记录、存储。

## 任务

- [ ] `pyproject.toml` + `uv.lock`，Python 3.12，依赖固定版本
- [ ] `src/codepilot/` 布局（见 02「目录结构」）
- [ ] pytest / ruff / mypy 配置；pytest marker：`docker`、`llm`、`slow`
- [ ] Pydantic Settings + `.env.example`（只含 key 名，不含值）
- [ ] `RepairState`、`RepairBudget`、`ExecutionResult` 等核心 Pydantic schema（见 02「LangGraph 编排」）
- [ ] `LLMProvider` Protocol，`OpenAICompatibleProvider` 实现
- [ ] `configs/llm.yaml`：内置 DeepSeek / Kimi / GLM 三个 provider 模板，包括模型能力字段、单价、角色到模型的映射（见 02「多 Provider 接入」）
- [ ] 能力差异处理：没有原生 tool calling 时降级为 JSON 工具协议；处理无 JSON 模式、忽略 temperature、剥离思考内容
- [ ] 错误统一映射为 `RateLimitError` / `ProviderError` / `ContextTooLongError`；每个 provider 有独立的并发上限
- [ ] 费用按模型单价计算并换算为 `budget_currency`；`max_cost` 由用户设定，可以为空
- [ ] `FakeLLM`：按脚本顺序返回预置响应，用于确定性测试
- [ ] `RecordingLLM` / `ReplayLLM`：记录每次调用到 `llm_calls.jsonl`，按 request hash 回放（见 02「LLM 调用层」）
- [ ] 结构化输出：JSON Schema → Pydantic 校验 → 失败带错误信息重试，最多 2 次
- [ ] 事件记录器：JSONL + 数据库 `events` 表
- [ ] SQLAlchemy 模型，默认 SQLite，`DATABASE_URL` 可切换 PostgreSQL
- [ ] CLI 入口 `codepilot`（Typer），子命令先留 `--help`
- [ ] FastAPI app + `GET /health`
- [ ] CI（GitHub Actions）：ruff + mypy + 非 docker、非 llm 的 pytest

## 验收

```bash
uv run pytest -m "not docker and not llm"
uv run ruff check .
uv run mypy src
uv run codepilot --help
```

- 全部通过；
- `RepairState` 能 JSON 序列化后完整还原（round-trip 测试）；
- 用 `RecordingLLM` 录一次结构化输出调用，`ReplayLLM` 回放结果逐字节一致；
- 结构化输出遇到非法 JSON 时会重试，重试耗尽后抛出明确的 `StructuredOutputError`，不吞异常。

# Phase 1：Repository Index

## 目标

输入一个本地 Python 仓库路径和 commit，输出 files / symbols / edges / tests，持久化并支持按文件 hash 增量重建。

## 任务

- [ ] `WorkspaceManager`：clone → checkout base commit → 复制到隔离 workspace，原始目录只读使用（见 02「Repository 获取与 Workspace 隔离」）
- [ ] `RepositoryScanner`：忽略规则 + `.gitignore`，跳过 >1MB 文件和二进制文件
- [ ] `PythonParser` 接口，Tree-sitter 实现；语法错误文件记录 `parse_error`，不中断整体索引
- [ ] Symbol 提取：module / class / function / method / nested function / test，qualified name 规则见 02
- [ ] Import 提取：`import a.b`、`from .x import y`、别名、相对导入解析到仓库内文件
- [ ] Call 提取 + 近似解析，每条边带 `confidence`（high / medium / low）
- [ ] Inherit 提取（同仓库内基类）
- [ ] 静态 Test → Symbol 关联（命名约定 + import + 调用）
- [ ] Git history：仅 base commit 的祖先提交，统计文件 / symbol 修改频率
- [ ] 索引持久化（SQLite）+ 按 `sha256` 增量更新
- [ ] `codepilot index <path> [--commit]` 命令
- [ ] `tests/fixtures/repos/` 下至少 3 个小型 fixture 仓库（含相对导入、继承、装饰器、嵌套函数、测试类）

## 验收

```bash
uv run codepilot index tests/fixtures/repos/mini_auth
```

输出 Files / Symbols（按类型）/ Edges（按类型和 confidence）/ Tests 计数。

- fixture 仓库上的 symbol 和 edge 与手写的期望 JSON 完全一致（golden test）；
- 在一个真实中型仓库（建议 `requests` 或 `flask` 固定 commit）上完成索引，耗时和计数写入 `docs/notes/phase1.md`；
- 修改一个文件后重新索引，只重新解析该文件（有测试断言）；
- Git history 不包含 base commit 之后的提交（有测试断言）。

# Phase 2：Retrieval

## 目标

Issue 文本 → Top-K 候选 symbol（函数级）和文件，各检索通道可单独开关，Recall@K 可自动计算。

## 任务

- [x] Query 构造：标识符、错误信息、文件路径、驼峰 / 下划线拆分、停用词表
- [x] Lexical 通道：ripgrep 精确匹配 + BM25（`rank_bm25` 或自实现），文档单位为 symbol
- [x] `EmbeddingProvider` 接口，本地模型和 API 两种实现；embedding 按内容 hash 缓存
- [x] 向量检索：numpy 暴力检索为默认，FAISS 为可选
- [x] Structural 通道：从种子 symbol 沿图扩展，按深度衰减
- [x] Test proximity 通道、History 通道
- [x] 分数归一化 + 加权融合，以及 RRF 融合作为对照（见 02「Retrieval」）
- [x] 函数级 → 文件级聚合
- [x] `RetrievalResult` 保存每个候选在各通道的原始分和归一化分，便于事后解释
- [x] Recall@K 评估器：文件级 + 函数级
- [x] 至少 10 个带 gold location 的检索评估样例

## 验收

```bash
uv run codepilot retrieve --repo tests/fixtures/repos/mini_auth --issue tests/fixtures/issues/expired_token.md
uv run codepilot eval-retrieval --dataset tests/fixtures/retrieval_cases.jsonl
```

- 输出每个通道单独启用时和融合后的 File / Function Recall@1/5/10 表格；
- 归一化函数、融合函数是纯函数，有单元测试；
- 检索结果确定：相同输入两次运行输出完全一致。

**2026-10-11 本地离线验收通过**：两条原样 CLI 均 exit 0；全量 1129 passed / 1 skipped / 1 deselected，覆盖率 94.91%，ruff / format / mypy 均通过。12 条合成开发样例输出六单通道及融合表；真实 Git / 索引、独立进程的原始 stdout / stderr / 完整评估 JSON 字节一致，基准后提交不可达。Semantic 行为明确标识的 offline-hash 非学习基线，真实模型 / API / GPU / Docker Sandbox / LLM / 远端 CI / 正式真实问题基准 NOT RUN；不宣称准确率提升。详见 [本地验收记录](notes/phase2-retrieval-eval.md) 与 [证据索引](evidence/phase2-retrieval-eval-20261011/README.md)。本轮不进入 Phase 3。

# Phase 3：Issue Analysis + Localization

## 目标

在检索结果之上做 LLM 分层定位：文件 → symbol → 行范围，产出给 Planner 用的定位结果。

## 任务

- [ ] `IssueAnalyzer`：规则抽取（traceback、代码块、路径、标识符）+ LLM 结构化抽取（`IssueAnalysis` schema）
- [ ] Traceback 中出现的仓库内文件 / 函数直接作为高优先级种子
- [ ] 文件级 rerank：给 LLM 看 Top-N 文件的骨架（类名、函数签名，不含函数体），选出 ≤3 个文件
- [ ] Symbol 级定位：给 LLM 看选中文件的骨架和相关函数体，选出 ≤5 个 symbol 和行范围
- [ ] 每一步保存 LLM 的选择理由
- [ ] Context Builder：按 token 预算截断，优先级规则见 02「Context 构造」
- [ ] `LocalizationResult` schema

## 验收

- 用 FakeLLM 跑通完整定位流程的确定性测试；
- 对 Phase 2 的检索评估集，用真实 LLM 跑一次，对比“仅检索”和“检索 + LLM rerank”的 Recall@1/5，结果和 `llm_calls.jsonl` 保存到 `artifacts/phase3/`；
- Context Builder 有测试证明：任何输入下输出 token 数不超过预算。

# Phase 6：Issue Reproduction

## 目标

在修复前先生成一个能复现问题的测试，作为 Agent 自己可用的“目标测试”。

这一阶段解决一个关键问题：在 SWE-bench 等真实评测中，用于判分的 FAIL_TO_PASS 测试在推理阶段不可见（见 01「评测协议与信息隔离」）。如果 Agent 只能依赖评测测试来判断修复是否成功，就等于偷看答案。

## 任务

- [x] `ReproductionAgent`：根据 Issue 和定位结果写一个复现测试文件，放在 `tests/_codepilot_repro/` 下
- [x] 在 base commit 上运行复现测试，必须 FAIL 才算有效复现；PASS 说明没复现，最多重试 3 次
- [x] 复现失败时降级：只使用仓库已有测试做回归，状态记为 `reproduction=failed`
- [x] 复现测试不进入最终提交的 patch（最终 diff 中剔除 `_codepilot_repro/`）
- [x] 复现测试文件不受“测试文件保护”限制，但已有测试仍然受保护

## 验收

- 在 synthetic fixture 上统计复现成功率（复现测试在 base 上 FAIL，在 gold patch 上 PASS 的比例），写入 `artifacts/phase6/`；这里使用 gold patch 只是为了评估复现测试本身的质量，属于离线评测，不在推理链路中；
- 有测试断言最终 patch 中不包含复现测试目录。

### 本轮实现记录（2026-10-20，M2 自验证闭环修复与预算机制加固）

分支 `codex/phase11-runtime-acceptance`，基线 HEAD `55a4380`。首次真实判分成功暴露的
不是模型缺陷而是工作流缺陷：`repair_patch` 的编码循环撞到每轮 30 次工具上限后，
`_run_coder` 把整个 run 写成 `budget_exhausted`，路由于是跳过 PatchValidator、目标测试、
回归与 PatchReviewer 直奔 finalize —— 补丁是对的，但 Agent 无法自证。

修法是把**局部额度**与**全局终止**分写成两层，而不是提高工具调用上限：

- 预算分四层各自成立：工具调用（局部，`max_tool_calls_per_iteration=30`，`CodingAgent`
  仍拒绝 >30）、修复迭代（`max_iterations`，首轮不计入）、模型与费用
  （`max_total_tokens` / `max_cost` + 派发级 `DispatchBudget` 硬账本）、验证与审查
  （`max_test_runs` 与**新增** `max_review_calls=2` 专属额度）。
- 编码阶段局部额度耗尽时：有补丁 → 冻结其 SHA-256、记 `coding_stop_reason`、继续走完
  校验/目标测试/回归/审查；无补丁 → 才是真终态并写明 `EMPTY_PATCH`。
- 编码派发前按现有费用模型**预留**验证、审查与那一次有界修复的资源：预留只收紧
  消耗型活动的可用上限（并在编码循环内每一圈判定），从不写入账本，因此不可能重复
  计费；未知费用 + 设了硬费用上限时 fail closed 阻断派发。
- 审查结论绑定被审补丁的 SHA-256，同版本重放复用（不重复调用、不重复计数），换版本
  立即作废；前置条件不满足时 `review` 节点**不调用模型**，把原因写进
  `review_skip_reason`，报告记 NOT EXECUTED。
- `RunReport.closure`（`VerificationClosure`）逐阶段回答"补丁/校验/目标测试/L1-L3/审查/

**1. 闭环预留的费用口径**。上一轮的预留按 `state.usage.cost / state.usage.total_tokens`
