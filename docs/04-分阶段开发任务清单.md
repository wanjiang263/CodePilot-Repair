# CodePilot-Repair 分阶段开发任务清单

> 版本：v1.1  
> 阶段编号以本文件为准，01 / 02 / 03 中提到的 Phase 均指本文件的编号。  
> 使用方法：按 Phase 顺序交给 Coding Agent（Codex / Claude Code）。每个 Phase 同时满足“通用完成标准”和本阶段“验收”后，才进入下一阶段。  
> 工作量按单人全职粗略估算，用于排期和发现偏差，不是承诺。

---

# 通用完成标准（每个 Phase 都适用）

- `uv run pytest` 通过，新增代码有对应测试；
- `uv run ruff check .`、`uv run mypy src` 无错误；
- 不依赖真实 LLM 的测试一律使用 FakeLLM 或录制回放（见 02「LLM 调用层」）；
- 需要真实 LLM 的验收写成脚本保存在 `scripts/`，可重复执行，运行产物保存在 `artifacts/`；
- 需要 Docker 的测试标记为 `@pytest.mark.docker`，Docker 不可用时自动 skip，并在汇报中说明；
- 文档同步更新；
- 汇报格式遵循 03-AGENTS.md §33，未实际执行的命令不得写 PASS。

# Phase 0：工程骨架 + LLM 调用层

## 目标

可运行、可测试的 Python 工程，后续所有模块都依赖的基础设施在这一阶段一次定好：配置、状态模型、LLM 抽象、事件记录、存储。

## 任务

- [ ] `pyproject.toml` + `uv.lock`，Python 3.12，依赖固定版本
- [ ] `src/codepilot/` 布局（见 02「目录结构」）
- [ ] pytest / ruff / mypy 配置；pytest marker：`docker`、`llm`、`slow`
- [ ] Pydantic Settings + `.env.example`（只含 key 名，不含值）
- [ ] `RepairState`、`RepairBudget`、`ExecutionResult` 等核心 Pydantic schema（见 02「LangGraph 编排」）
- [ ] `LLMProvider` Protocol，`OpenAICompatibleProvider` 实现
- [ ] `configs/llm.yaml`：内置 DeepSeek / Kimi / GLM 三个 provider 模板，包括模型能力字段、单价、角色到模型的映射（见 02「多 Provider 接入」）
- [ ] 能力差异处理：没有原生 tool calling 时降级为 JSON 工具协议；处理无 JSON 模式、忽略 temperature、剥离思考内容
- [ ] 错误统一映射为 `RateLimitError` / `ProviderError` / `ContextTooLongError`；每个 provider 有独立的并发上限
- [ ] 费用按模型单价计算并换算为 `budget_currency`；`max_cost` 由用户设定，可以为空
- [ ] `FakeLLM`：按脚本顺序返回预置响应，用于确定性测试
- [ ] `RecordingLLM` / `ReplayLLM`：记录每次调用到 `llm_calls.jsonl`，按 request hash 回放（见 02「LLM 调用层」）
- [ ] 结构化输出：JSON Schema → Pydantic 校验 → 失败带错误信息重试，最多 2 次
- [ ] 事件记录器：JSONL + 数据库 `events` 表
- [ ] SQLAlchemy 模型，默认 SQLite，`DATABASE_URL` 可切换 PostgreSQL
- [ ] CLI 入口 `codepilot`（Typer），子命令先留 `--help`
- [ ] FastAPI app + `GET /health`
- [ ] CI（GitHub Actions）：ruff + mypy + 非 docker、非 llm 的 pytest

## 验收

```bash
uv run pytest -m "not docker and not llm"
uv run ruff check .
uv run mypy src
uv run codepilot --help
```

- 全部通过；
- `RepairState` 能 JSON 序列化后完整还原（round-trip 测试）；
- 用 `RecordingLLM` 录一次结构化输出调用，`ReplayLLM` 回放结果逐字节一致；
- 结构化输出遇到非法 JSON 时会重试，重试耗尽后抛出明确的 `StructuredOutputError`，不吞异常。

# Phase 1：Repository Index

## 目标

输入一个本地 Python 仓库路径和 commit，输出 files / symbols / edges / tests，持久化并支持按文件 hash 增量重建。

## 任务

- [ ] `WorkspaceManager`：clone → checkout base commit → 复制到隔离 workspace，原始目录只读使用（见 02「Repository 获取与 Workspace 隔离」）
- [ ] `RepositoryScanner`：忽略规则 + `.gitignore`，跳过 >1MB 文件和二进制文件
- [ ] `PythonParser` 接口，Tree-sitter 实现；语法错误文件记录 `parse_error`，不中断整体索引
- [ ] Symbol 提取：module / class / function / method / nested function / test，qualified name 规则见 02
- [ ] Import 提取：`import a.b`、`from .x import y`、别名、相对导入解析到仓库内文件
- [ ] Call 提取 + 近似解析，每条边带 `confidence`（high / medium / low）
- [ ] Inherit 提取（同仓库内基类）
- [ ] 静态 Test → Symbol 关联（命名约定 + import + 调用）
- [ ] Git history：仅 base commit 的祖先提交，统计文件 / symbol 修改频率
- [ ] 索引持久化（SQLite）+ 按 `sha256` 增量更新
- [ ] `codepilot index <path> [--commit]` 命令
- [ ] `tests/fixtures/repos/` 下至少 3 个小型 fixture 仓库（含相对导入、继承、装饰器、嵌套函数、测试类）

## 验收

```bash
uv run codepilot index tests/fixtures/repos/mini_auth
```

输出 Files / Symbols（按类型）/ Edges（按类型和 confidence）/ Tests 计数。

- fixture 仓库上的 symbol 和 edge 与手写的期望 JSON 完全一致（golden test）；
- 在一个真实中型仓库（建议 `requests` 或 `flask` 固定 commit）上完成索引，耗时和计数写入 `docs/notes/phase1.md`；
- 修改一个文件后重新索引，只重新解析该文件（有测试断言）；
- Git history 不包含 base commit 之后的提交（有测试断言）。

# Phase 2：Retrieval

## 目标

Issue 文本 → Top-K 候选 symbol（函数级）和文件，各检索通道可单独开关，Recall@K 可自动计算。

## 任务

- [x] Query 构造：标识符、错误信息、文件路径、驼峰 / 下划线拆分、停用词表
- [x] Lexical 通道：ripgrep 精确匹配 + BM25（`rank_bm25` 或自实现），文档单位为 symbol
- [x] `EmbeddingProvider` 接口，本地模型和 API 两种实现；embedding 按内容 hash 缓存
- [x] 向量检索：numpy 暴力检索为默认，FAISS 为可选
- [x] Structural 通道：从种子 symbol 沿图扩展，按深度衰减
- [x] Test proximity 通道、History 通道
- [x] 分数归一化 + 加权融合，以及 RRF 融合作为对照（见 02「Retrieval」）
- [x] 函数级 → 文件级聚合
- [x] `RetrievalResult` 保存每个候选在各通道的原始分和归一化分，便于事后解释
- [x] Recall@K 评估器：文件级 + 函数级
- [x] 至少 10 个带 gold location 的检索评估样例

## 验收

```bash
uv run codepilot retrieve --repo tests/fixtures/repos/mini_auth --issue tests/fixtures/issues/expired_token.md
uv run codepilot eval-retrieval --dataset tests/fixtures/retrieval_cases.jsonl
```

- 输出每个通道单独启用时和融合后的 File / Function Recall@1/5/10 表格；
- 归一化函数、融合函数是纯函数，有单元测试；
- 检索结果确定：相同输入两次运行输出完全一致。

**2026-10-11 本地离线验收通过**：两条原样 CLI 均 exit 0；全量 1129 passed / 1 skipped / 1 deselected，覆盖率 94.91%，ruff / format / mypy 均通过。12 条合成开发样例输出六单通道及融合表；真实 Git / 索引、独立进程的原始 stdout / stderr / 完整评估 JSON 字节一致，基准后提交不可达。Semantic 行为明确标识的 offline-hash 非学习基线，真实模型 / API / GPU / Docker Sandbox / LLM / 远端 CI / 正式真实问题基准 NOT RUN；不宣称准确率提升。详见 [本地验收记录](notes/phase2-retrieval-eval.md) 与 [证据索引](evidence/phase2-retrieval-eval-20261011/README.md)。本轮不进入 Phase 3。

# Phase 3：Issue Analysis + Localization

## 目标

在检索结果之上做 LLM 分层定位：文件 → symbol → 行范围，产出给 Planner 用的定位结果。

## 任务

- [ ] `IssueAnalyzer`：规则抽取（traceback、代码块、路径、标识符）+ LLM 结构化抽取（`IssueAnalysis` schema）
- [ ] Traceback 中出现的仓库内文件 / 函数直接作为高优先级种子
- [ ] 文件级 rerank：给 LLM 看 Top-N 文件的骨架（类名、函数签名，不含函数体），选出 ≤3 个文件
- [ ] Symbol 级定位：给 LLM 看选中文件的骨架和相关函数体，选出 ≤5 个 symbol 和行范围
- [ ] 每一步保存 LLM 的选择理由
- [ ] Context Builder：按 token 预算截断，优先级规则见 02「Context 构造」
- [ ] `LocalizationResult` schema

## 验收

- 用 FakeLLM 跑通完整定位流程的确定性测试；
- 对 Phase 2 的检索评估集，用真实 LLM 跑一次，对比“仅检索”和“检索 + LLM rerank”的 Recall@1/5，结果和 `llm_calls.jsonl` 保存到 `artifacts/phase3/`；
- Context Builder 有测试证明：任何输入下输出 token 数不超过预算。

# Phase 4：Sandbox + 环境构建

## 目标

在 Docker 里为仓库构建可运行测试的环境，执行任意测试子集并得到结构化结果；记录 base commit 上的测试基线。

## 任务

- [ ] `Sandbox` 接口 + `DockerSandbox` 实现（docker SDK for Python）
- [ ] 两阶段执行：环境构建阶段允许网络；测试执行阶段 `network_mode=none`（见 02「Sandbox 与环境构建」）
- [ ] 环境镜像按 `(repo, base_commit, env_spec hash)` 缓存
- [ ] `EnvSpec`：Python 版本、安装命令、测试命令、环境变量；fixture 和 SWE-bench 各有一种来源
- [ ] 资源限制：CPU、内存、pids、超时；非 root；只读根文件系统 + 可写 `/workspace` 与 `/tmp`
- [ ] 超时后强制 kill 并清理容器，防止泄漏
- [ ] pytest 结果通过 `--junitxml` 解析，不靠解析终端文本
- [ ] stdout / stderr 截断到可配置上限，完整内容存 artifact
- [ ] `ExecutionResult` 状态判定规则（见 02「ExecutionResult」）
- [ ] `TestBaseline`：在 base commit 上跑一次全量测试，记录每个测试的初始状态（pass / fail / error / skip）
- [ ] 失败的环境构建返回 `ENV_ERROR`，不进入修复流程
- [ ] Windows 下通过 Docker Desktop（WSL2 后端）运行，路径处理有测试

## 验收

```bash
uv run codepilot run-tests --repo tests/fixtures/repos/mini_auth --tests "tests/test_auth.py::test_login"
```

- 输出 `ExecutionResult` JSON，tests_passed / tests_failed 与 junit 一致；
- 以下行为都有 `@pytest.mark.docker` 测试：死循环测试被超时终止且状态为 `TIMEOUT`；测试中访问网络失败；容器内用户不是 root；内存超限被 OOM kill 后状态正确；运行结束后没有残留容器；
- 同一环境第二次运行命中镜像缓存，耗时写入 `docs/notes/phase4.md`。

# Phase 5：Planning + Coding + Patch Validation（M1）

## 目标

Issue → Plan → Patch → 校验 → 在 Docker 中测试 → Run Report。只生成一次 Patch，不迭代。

## 任务

- [ ] `ImpactAnalyzer`：基于图的 callers / callees / tests / 风险规则
- [ ] `Planner`：只读工具，输出 `RepairPlan`
- [ ] Coding Agent 工具集（见 02「Coding Agent 与工具」），每个工具有输入输出 schema 和单元测试
- [ ] 编辑格式：search/replace 块为主格式，unified diff 为备选（见 02「Patch 格式」）
- [ ] search 块匹配失败时返回最相近的片段，让 Agent 自行修正，最多重试 3 次
- [ ] 工具调用次数上限（默认 30 次/轮），超限结束本轮
- [ ] `PatchValidator`：路径、语法（`ast.parse`）、改动规模、测试文件保护、作弊模式检测（见 02「Patch Validator」）
- [ ] 补丁统一转成 `git diff` 保存
- [ ] LangGraph 最小图：understand → retrieve → localize → plan → generate → validate → run_tests → finalize
- [ ] `codepilot solve --repo ... --issue ...` 命令
- [ ] Run Report（JSON + Markdown），内容见 02「Run Report」

## 验收

- FakeLLM 驱动的端到端测试：在 fixture 仓库上生成预置补丁、校验通过、Docker 测试通过、Report 生成；
- PatchValidator 对以下每种作弊补丁都有拒绝测试：删除测试函数、加 `@pytest.mark.skip`、加 `xfail`、删除 `assert`、把 assert 改成恒真、修改 `conftest.py`、修改 CI 配置、在被测函数里硬编码测试期望值（启发式）；
- 真实 LLM 在 5 个 synthetic fixture 上各跑一次，结果和成本写入 `artifacts/phase5/`，成功率是多少就写多少。

# Phase 6：Issue Reproduction

## 目标

在修复前先生成一个能复现问题的测试，作为 Agent 自己可用的“目标测试”。

这一阶段解决一个关键问题：在 SWE-bench 等真实评测中，用于判分的 FAIL_TO_PASS 测试在推理阶段不可见（见 01「评测协议与信息隔离」）。如果 Agent 只能依赖评测测试来判断修复是否成功，就等于偷看答案。

## 任务

- [ ] `ReproductionAgent`：根据 Issue 和定位结果写一个复现测试文件，放在 `tests/_codepilot_repro/` 下
- [ ] 在 base commit 上运行复现测试，必须 FAIL 才算有效复现；PASS 说明没复现，最多重试 3 次
- [ ] 复现失败时降级：只使用仓库已有测试做回归，状态记为 `reproduction=failed`
- [ ] 复现测试不进入最终提交的 patch（最终 diff 中剔除 `_codepilot_repro/`）
- [ ] 复现测试文件不受“测试文件保护”限制，但已有测试仍然受保护

## 验收

- 在 synthetic fixture 上统计复现成功率（复现测试在 base 上 FAIL，在 gold patch 上 PASS 的比例），写入 `artifacts/phase6/`；这里使用 gold patch 只是为了评估复现测试本身的质量，属于离线评测，不在推理链路中；
- 有测试断言最终 patch 中不包含复现测试目录。

# Phase 7：Failure Diagnosis

## 目标

把测试失败输出转成结构化、有证据、体积受控的诊断结果。

## 任务

- [ ] junit XML 解析：每个失败测试的名称、类型、message、traceback
- [ ] Traceback 解析：帧列表，区分仓库内代码帧与第三方库帧，定位最深的仓库内帧
- [ ] 规则分类器（见 02「Failure Classifier」），规则未命中才调用 LLM
- [ ] 日志压缩：同类失败去重、只保留仓库内帧、超长输出截断
- [ ] `FailureSignature`：异常类型 + 仓库内最深帧位置 + 归一化 message（去掉地址、数字等），用于重复检测
- [ ] `DiagnosisAgent`：输入压缩后的失败、相关源码、本轮 patch、历史诊断；输出带 evidence 的 `Diagnosis`
- [ ] Evidence 校验：evidence 中引用的 `file:line` 必须真实存在，否则剔除并降低 confidence

## 验收

- 至少 15 份真实 pytest 输出样本（覆盖 SyntaxError、ImportError、AttributeError、TypeError、KeyError、AssertionError、超时、收集错误、fixture 错误）存在 `tests/fixtures/failures/`，解析和分类结果有 golden test；
- 压缩后的失败上下文不超过配置的 token 上限；
- 相同根因、不同内存地址的两次失败得到相同的 `FailureSignature`。

# Phase 8：Iterative Repair（完整 LangGraph）

## 目标

把 Phase 5–7 组装成带条件路由、预算和停止规则的完整状态机。

## 任务

- [ ] 完整 LangGraph 图（见 02「LangGraph 编排」），每个节点是独立函数，输入输出都是 `RepairState`
- [ ] `BudgetManager`：迭代次数、测试运行次数、token、费用、墙钟时间；每个节点进入前检查
- [ ] `ProgressTracker`：按 02「进度判定」计算每轮是否有进展
- [ ] 停止规则：重复 FailureSignature、重复 patch hash、连续两轮无进展、sandbox 连续失败、预算耗尽；每个停止原因对应一个明确的 `stop_reason`
- [ ] 修复策略：基于当前 patch 增量修改，或回退到 base 重新生成（见 02「修复策略」）
- [ ] 每轮的 patch、执行结果、诊断都写入历史，不覆盖
- [ ] LangGraph checkpointer（SQLite），任务中断后可从最后一个节点恢复
- [ ] `recursion_limit` 设为预算推导出的上限，作为最后一道防线

## 验收

- FakeLLM 驱动的图测试覆盖以下路径，每条路径一个测试：一次通过；第 1 轮失败、第 2 轮通过；重复失败触发停止；重复 patch 触发停止；无进展触发停止；预算耗尽停止；sandbox 错误停止；校验失败后重新生成；
- 中断恢复测试：在 `run_tests` 节点后杀掉进程，恢复后从下一个节点继续，不重复已完成的节点；
- 任何路径下图都会在有限步数内结束（参数化测试 + `recursion_limit` 断言）。

# Phase 9：Regression + Review + Run Report（M2）

## 目标

成功判定从“目标测试通过”升级为“目标通过 + 回归无新增失败 + Review 通过”。

## 任务

- [ ] 三级测试：复现测试 / 目标测试 → affected tests → 全量回归
- [ ] 回归判定以 Phase 4 的 `TestBaseline` 为准：只有“base 上 PASS、patch 后 FAIL”的测试算回归；base 上本来就失败的测试不算（见 02「Regression 判定」）
- [ ] Flaky 处理：新出现的失败重跑 2 次，结果不一致标记为 flaky，不计入回归
- [ ] 全量回归超过时间预算时，降级为 affected tests + 随机抽样，并在 Report 中标注
- [ ] `PatchReviewer`：只读，输入 issue / plan / diff / 测试结果，输出 `ReviewResult`
- [ ] Review 拒绝时带具体问题，回到 repair 节点，计入迭代预算
- [ ] 最终 Run Report：patch、每轮记录、测试结果、Review、token、费用、耗时、stop_reason

## 验收

- 构造一个“修复目标 bug 但破坏另一个函数”的 fixture，系统能识别回归并继续修复或以 `regression` 原因停止；
- 构造一个 base 上就有失败测试的 fixture，系统不把已有失败算作回归；
- 构造一个 flaky 测试的 fixture，系统能识别为 flaky；
- 在全部 synthetic fixture 上用真实 LLM 端到端跑一次，产出 Run Report。

# Phase 12：Ablation + 实验报告（M4）

## 目标

用对照实验回答“每个组件是否有用、有多大用”。

## 实验矩阵

| 组 | 配置 | 回答的问题 |
|---|---|---|
| A | 无检索：只给 Issue + 文件列表，单次生成 | 下界 |
| B | BM25 检索，单次生成 | 词法检索的贡献 |
| C | BM25 + 语义检索，单次生成 | 语义检索的增量 |
| D | 全部检索通道 + 图扩展，单次生成 | 结构信息的增量 |
| E | D + 迭代修复（只给原始日志） | 迭代本身的贡献 |
| F | D + 迭代修复 + 结构化诊断 | 诊断的增量 |
| G | F + 复现测试 + Review（完整系统） | 完整系统 |

最低保留：A、D、G 三组。

## 任务

- [ ] 每组一个配置文件，只改变一个变量
- [ ] synthetic 集每组 3 个 seed；SWE-bench 50 题子集每组 1 次

- [ ] 成本对比：每组每题平均 token、费用、耗时
- [ ] 失败案例分析：随机抽 20 个失败任务，人工归类失败原因（定位错 / 理解错 / 改错 / 环境问题 / 超预算）
- [ ] 输出 `ablation/results.csv`、`ablation/metrics.json`、`docs/experiment-report.md`

## 验收

- 报告中每个数字都能追溯到 `artifacts/` 中的具体运行目录；
- 没有显著差异的组件如实写“未观察到显著提升”。
