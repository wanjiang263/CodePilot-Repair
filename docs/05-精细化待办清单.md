## 0. 怎么用这份清单

1. **按波次推进，不按 Phase 推进**。Phase 是验收单位，wave 是执行单位。同一 wave 内的任务没有相互依赖，可以任意顺序做，也可以并行。
2. **一次只做一个任务**。每个任务的「验收」一栏写了证明它完成的**具体测试或命令**。测试没写出来，任务就没完成（03 §22）。
3. **接口先行**。§1.3 的接口冻结清单是跨簇契约。实现方按它提供，消费方按它调用；要改接口，先改这份清单，再改代码。
4. **每个 Phase 结束时**跑 03 §32 的阶段完成规则（pytest + ruff + mypy + 文档 + 04 的 Phase 验收），**全部通过才算完成**；任何一条没实际跑过，就写 NOT RUN，不得写 PASS（03 §33）。
5. **需要真实 LLM 的验收**一律写成 `scripts/` 下的脚本，产物落 `artifacts/`，数字是多少写多少。
6. **需要 Docker 的验收**标记 `@pytest.mark.docker`；Docker 不可用时自动 skip，并在汇报里写明 NOT RUN。

Phase 4～Phase 14 每次开发与阶段收口时，按固定 ID 复查 [Deferred Acceptance / Technical Debt Register](#deferred-acceptance-register)，仅更新受影响项；未执行验收不得因后续离线门禁通过而关闭。

> **环境记录**：2026-10-08 Docker 未安装；2026-10-10 Docker Desktop Linux daemon 已可用（29.8.2），Phase 1 容器索引验收另行记录。`uv` 位于 `~/.local/bin/uv.exe`，项目命令使用虚拟环境；不能再将旧环境限制当作当前无法执行 Docker 的原因。

## 1. 模块分解与架构依赖关系

### 1.1 分层视图

依赖严格单向向下，同层之间不允许互相 import（唯一例外是 §1.3 明确列出的接口调用）。

```text
┌─ L4 编排层 ────────────────────────────────────────────────┐
│  graph/  LangGraph 状态机 · 预算 · 进度 · 停止规则 · 回归      │
└────────────────────────┬───────────────────────────────────┘
┌─ L3 智能体层 ──────────▼───────────────────────────────────┐
│  retrieval/   agents/   tools/   patch/   failure/          │
└────────────────────────┬───────────────────────────────────┘
┌─ L2 领域能力层 ────────▼───────────────────────────────────┐
│  repo/   sandbox/   context/                                │
└────────────────────────┬───────────────────────────────────┘
┌─ L1 基础设施层 ────────▼───────────────────────────────────┐
│  llm/   storage/   observability/                           │
└────────────────────────┬───────────────────────────────────┘
┌─ L0 契约层 ────────────▼───────────────────────────────────┐
│  schemas/   config.py   （纯数据，无副作用，无外部依赖）        │
└────────────────────────────────────────────────────────────┘
        eval/ 与 api/ 在最右侧，只允许依赖 L0–L4，不被任何层依赖
```

**这条分层的硬约束**：`repo/` 不许 import `agents/`；`sandbox/` 不许 import `graph/`；`llm/` 不许知道 `patch/` 的存在。违反即耦合泄漏，Review 时直接打回。

## 3. 关键路径与里程碑

关键路径 = 决定项目最早完成时间的任务链。**这条链上任一任务延期，交付就延期**；不在链上的任务可以并行追赶。

```text
【到 M1 的最短路径】(约 8 周)
F-01 → F-08 → F-14/15/16 → F-11/12 → L-03 → L-05 → L-09 → L-10
  → R-01 → R-05 → R-06 → R-09 → R-16 → R-17
  → V-01 → V-04 → V-15 → V-16
  → C-02 → C-05 → C-09 → C-10
  → S-04 → S-05 → S-06 → S-11 → S-12
  → P-06 → P-09 → P-14 → P-16 → P-21 → P-22 → P-24
关键路径长度 ≈ 37 个任务

【M1 → M2 的增量路径】(约 3 周)
D-02 → D-11 → D-14 → D-16 → D-21
  → G-01 → G-04 → G-08 → G-09 → G-12
  → G-26 → G-27 → G-31
增量 ≈ 15 个任务

【M2 → M3 的增量路径】(约 2 周)
E-01 → E-11 → E-12 → E-14 → E-16 → E-17 → E-18
增量 ≈ 7 个任务

【M3 → M4 的增量路径】(约 1.5 周)
E-21 → E-22 → E-23 → E-26
增量 ≈ 4 个任务
```

**里程碑可验证条件**

|---|---|---|
| **M1** 最小闭环 | W18 末 | 单次生成：Issue → 定位 → Plan → Patch → 校验 → Docker 测试 → Report。**没有迭代修复**。FakeLLM+FakeSandbox 端到端测试通过；真实 LLM 在 5 个 fixture 上跑过一次，成功率如实记录在 `artifacts/phase5/` |

**两个把接口定下来的实测结论**（都不是设计推导出来的，是量出来的）：

1. **IR 必须是惰性视图，不能是转换后的对象树。** 原设计把 tree-sitter 节点递归转成 frozen dataclass。实测：一个 0.69MB 源文件有 30 万个节点，转换耗时 **1561ms**，而 tree-sitter 自己解析只要 **124ms**——包装比被包装的对象慢 12 倍，内存下界 23MB/文件。改成零转换的转发 `Protocol` 后遍历 30 万节点是 **58ms**。
2. **`decorated_definition` 的装饰器没有具名字段。** 实测 `field_name_for_child` 对它返回 `None`、`children_by_field_name("decorator")` 返回 0 个。按字段取会静默得到空列表——症状是"所有函数的装饰器都是空的"，而且不报错。

**被测试抓出的真实缺陷（续第 7–9 条，这里是第 10–12 条）**：

| # | 缺陷 | 症状 | 根因 |
|---|---|---|---|
| 10 | `run_git` 的 `timeout` 不是超时 | `subprocess.run` 超时后只杀直接子进程，再 `communicate()` 把管道读到 EOF，而继承了管道的孙进程握着它不放。`git clone` 正是这种形状（派生 `git-remote-https`/`ssh`）。实测 `timeout=2` **实际 8.2 秒**才抛 `TimeoutExpired`；孙进程若永不退出（挂住的 ssh），这个等待**没有上界** | 改为自己管理 `Popen` 生命周期，超时后杀整棵进程树（POSIX `killpg` / Windows `taskkill /T`），再给管道一个有上界的收尾 |
| 11 | 超时处理路径里藏着一个无上界的阻塞调用 | `taskkill` 本身是对着出问题的进程树跑的，卡住并不罕见。实测中它一次吃掉了 25 秒——"超时"两个字被取消 | 给 `taskkill` 那次 `subprocess.run` 加 `timeout`；它自己的超时不是靠它实现，只能显式传 |

#### 一处**变异存活**，如实记下

`test_copy_mode_creates_an_independent_clone` 断言"workspace 与缓存不共享对象 inode"，但把 `_clone_copy` 的 `--no-hardlinks` 删掉它**仍然通过**：紧接着的 `_truncate_history_to` 会跑 `git gc --prune=now`，重新打包整个对象库，硬链接进来的 pack 被替换掉了。所以那个可观察性质无论有没有这个参数都成立，变异检测不到。

那个参数仍然保留——它是 gc 那一步没跑成时的兜底（`gc` 的 `check=False` 意味着失败不中断创建），此时硬链接会原样留在磁盘上。这条局限已写进测试的 docstring。

另外：第一版 `_object_inodes()` 只认 `.git/objects`，而缓存是 bare 仓库（对象在 `objects/`）→ 那边永远返回空集 → 交集恒为空 → 断言无论如何都通过。**同样是变异测试发现的**，已改成两种布局都认。

### 12.1 Phase 8 完成记录（2026-10-15）

G-01～G-24 **IMPLEMENTED / PASS**（离线工程验收），逐条实现文件与测试证据见
[Phase 8 完整记录](notes/phase8.md)。要点与偏差：

* **真的在跑 StateGraph**：八条标准路径与 12 种终止形状都通过 `StateGraph` 执行，
  断言节点轨迹与 superstep 数，而不是直接调用路由函数或把 Phase 5 的 solve 套一层
  循环。`tests/graph` + `tests/unit/graph` 合计 **301 passed**（含 1 项真实 Docker）。
* **两种 checkpoint 口径是实测出来的**：LangGraph 默认 `durability="async"`，实测在
  节点执行完之后硬杀进程会丢掉该节点的 checkpoint，恢复只能从头重跑，因此运行入口
  显式 `durability="sync"`；`durability` 必须是 `invoke` 的关键字参数，塞进 `config`
  会被静默忽略。节点是 `async def` ⇒ 只能 `ainvoke` ⇒ 必须用 `AsyncSqliteSaver`
  （`aiosqlite` 是 `langgraph-checkpoint-sqlite` 的既有依赖，未新增包）。"下一步跑哪个
  节点"要读 `aget_state().next`，原始 `checkpoint["next"]` 实测在崩溃后为空。
* **SQLite 存下的只是 state**：Workspace、容器结果、Artifact 都在 checkpoint 之外。
  恢复前三段核对（Workspace 存在 / base commit 一致 / 补丁哈希一致 / Artifact 可读），
  证据失效就关闭复用开关并重新执行、重新计费；Workspace 缺失或 base commit 不匹配时
  **拒绝继续**。本轮承诺的是 at-most-once-with-verified-evidence，**不**宣称 exactly-once。
  为此 `run_target_tests` 改为当轮就落 `execution.json`——只在 finalize 写的话，崩溃的
  run 一个执行 Artifact 都没有。
* **Patch hash 不"去掉所有空白"**（对 02 §15.5 表述的偏差，已在 §15.5 与本表同步）：
  Python 缩进是语法、三引号字符串行尾空格是数据。只归一化 `index`/`---`/`+++` 等无内容
  元数据与 CRLF，`\ No newline` 转成显式 `!NOEOL!` 参与哈希；正文逐字保留。
* **DA-010 的缓解要两条规则一起做**：第一版只给 `repeated_failure` 加失败身份核验，
  集成测试立刻暴露 `no_progress` 仍会因"签名回到过更早一轮"把 run 停在同一处。现在
  两条规则共用同一核验，仅签名一致而身份不同只记录、不停止。**未改**冻结 SHA1 算法，
  DA-010 保持 PENDING。
* **Phase 9 边界不伪造**：`run_regression` / `review` 是真实节点，但本轮无实现，
  记录 `DEFERRED:phase9-not-implemented` 且 `regression` / `review` 保持 `None`。
  `ProgressSnapshot` 新增带默认值的可选字段 `regression_measured`，否则"未测量"会被
  `made_progress` 读成"0 个新增回归"从而凭空制造进展。成功范围仍是
  `provisionally_verified`，未宣称 M2。
* **一条被纠正的测试预期**：refine 无法撤销已落盘的错误写入（模型把受保护文件写进
  Workspace 后，后续轮次只会继续叠加），因此"无效补丁 → 立刻变有效"不成立，真实的
  恢复路径是连续无效直到 `validation_loop`；测试按事实断言。
* **最终离线门禁的实测数字**：`pytest -m "not docker and not llm" --cov` =
  **2419 passed / 0 failed / 1 skipped / 30 deselected**，覆盖率 **93.81%**（阈值

  计时踩线失败（本轮未触碰 `repo/gitcmd.py` 与该测试文件；隔离重跑三次 77.59s /
  8.90s / 137.99s 均通过，同一用例墙钟差 15 倍）。**未 skip、未放宽断言**，按已知
  负载敏感用例登记，收紧计时预算归 Phase 1 的测试维护。

## 23.1 Q12：workspace 泄露 base 之后的提交（copy 模式已修；worktree 模式由 02 §13 的挂载策略覆盖）

**实测（本机 Windows 11 + git 2.51.1）**：workspace 建好之后，从它内部执行——

```text
git log --all          → 473f4ad fix: return 2 | 2721cb4 initial
git show v-fix:app.py  → 'def f():\n    return 2  # THE FIX'
git branch -a          → main（指向 base 之后）
```

worktree 模式与 copy 模式**都是这样**：worktree 与缓存共享同一份对象库和全部 refs；copy 模式的 `git clone` 把远端全部分支与标签一起复制了进来。

**为什么这是硬伤**：`03 §11.2` 把"看不到 base 之后的提交"定为硬性规则，而 SWE-bench 的 gold patch 就在那里。如果评测里 agent 能读到它，resolve 率这个数字就失去意义——不是"偏高"，是**不能报告**。03 §2.2 明令不得把数字建立在假实现上。

### 更正：这一条不是未决问题（2026-10-08 复核）

第一版把这里写成"阻塞 M3、实施前必须先定夺"，**过重了**。复核 `02 §13.2/§13.3` 的原文后确认，挂载策略本来就已经规定：

```text
阶段 1：环境构建（允许网络）→ 复制 base commit 的仓库 → EnvSpec.install
阶段 2：测试执行（network=none）→ 挂载本次 workspace（只包含 patch 后的源码）
/workspace 以可写方式挂载，/out 用于收集结果
```

缓存（含 gold patch 的 refs 与 objects）在容器之外。因此**在 02 规定的部署下，这条泄露对 agent 不可达**——agent 的工具集也跑不了 `git log --all`。所以它不是一个"必须先定夺才能开工"的阻塞项，而是"实现时要照着 02 §13 来"的约束。

### 但有两个我实测出来的残留，值得记清楚

**残留一：worktree 模式在宿主侧的暴露，本地无解。** 试过 alternates 这条常见路子（`git clone --reference <cache>`，让 workspace 有自己的 refs、对象走 alternates）：`git log --all` 确实变干净了，但 `git show <base 之后的 SHA>` **返回 0、读得到内容**，`cat-file --batch-all-objects` 里也有那个对象，`fsck --lost-found` 还能捞回来。**只要共享对象库，就一定有办法枚举出来。** 所以 worktree 模式在宿主侧不泄露这件事做不到，它只能靠沙箱边界。这一条已钉成 `test_worktree_is_the_only_mode_that_exposes_base_descendants`（同时断言 copy / fetch 不泄露）——哪天它变红了，说明该来更新这里的记录。

**残留二（新发现，功能问题而非隔离问题）：worktree 模式下沙箱里用不了 git。** `<workspace>/.git` 是一个内容为**宿主绝对路径**的文件，而 02 §13 只挂 `/workspace`，那个路径在容器里不存在。实测模拟（把缓存改名等价于容器内看不到它）：`git log` / `git describe` / `git status` 全部 `fatal: not a git repository`。

### 已找到第三种方案：fetch 模式（2026-10-09）

**问题**：worktree 快（0.34s）但沙箱内没有 git；copy 自包含（2.36s）但慢。能不能兼得？

**实测（requests v2.31.0，6155 个祖先提交）**：

```bash
git init --template= ws_fetch
git -C ws_fetch -c gc.auto=0 fetch --no-tags --stdin <cache> <<EOF
<base-sha>
<merged-tags-refspecs>
EOF
git -C ws_fetch checkout --detach <base>
```

- **耗时**：2.00s（fetch 本身 1.69s），比 copy 的 2.36s 还快
- **体积**：13MB，与 copy 相同
- **隔离**：`git show <fix>` 返回 128、`cat-file --batch-all-objects` 里 0 个 fix 对象
- **沙箱内 git**：`.git` 是目录，`git log`/`status`/`describe` 全部可用（实测 rc=0）
- **describe 可用**：输出 `v2.31.0-0-g147c8511`（当前 copy 模式因删掉全部 ref 而 `fatal: No names found`）

| 模式 | `.git` | 自包含 | 容器内 git 可用 | 宿主侧能看到 base 之后 | 耗时（6k 提交） | .git 体积 |
|---|---|---|---|---|---|---|
| worktree | 文件（宿主路径） | 否 | **否** | 是 | 0.34s | 共享缓存 |
| copy（当前） | 目录 | 是 | 是 | 否（已截断） | 2.36s | 13MB |
| **fetch（新）** | **目录** | **是** | **是** | **否** | **2.00s** | **13MB** |

影响范围有限但真实：阶段 1 的环境构建是在容器里**复制**一份仓库做的，所以 `pip install -e .` 之类不受影响；受影响的是**阶段 2 里运行时会去调 git 的测试**（版本号推导、检查工作区状态之类）。`Workspace.self_contained` 把这件事变成可断言的属性，沙箱层与 R-13 应当用它而不是靠"记得文档里那条规则"。

**结论（Q13 已定，已实施）**：**fetch 模式为默认**，worktree 作为"快速但不隔离"的可选项（CLI 场景、用户明确不在意泄露时）。fetch 在隔离性、沙箱兼容性上与 copy 持平，略快于 copy，体积相同；**比 worktree 慢约 6 倍**，这是为自包含与不泄露付的代价。

实施要点（`WorkspaceManager._fetch_base`）：

- refspec 只有 base SHA 与 `for-each-ref --merged <base> refs/tags/` 的结果，不加远端、不建分支。
- **分批放在命令行上，没有用 `--stdin`**：`run_git` 是文本模式，Windows 上写入的 `
` 变成 `
`，实测 git 报 `invalid refspec '<sha>
'`。按 24K 字符预算分批，避开 32K 命令行上限。
- `--no-tags` 保留但不承重：自动跟随只会拉指向已下载对象（全是 base 祖先）的 tag，不会引入泄露。变异验证中删掉它没有测试变红，属等价变异。

测试：`test_self_contained_workspace_has_no_commits_after_base[fetch|copy]`、`..._keeps_the_ancestors_of_base[fetch|copy]`、`test_fetch_mode_keeps_tags_merged_into_base`（describe 可用且 base 之后的 tag 不在）、`test_fetch_mode_survives_without_the_cache`、`test_fetch_mode_does_not_modify_the_cache`、`test_fetch_mode_batches_many_tags`、`test_default_mode_is_fetch`。变异（去掉 `--merged`、refspec 改成 `+refs/*:refs/*`、不取 tag、只跑第一批、加远端、默认值改回 worktree）各自至少让一条变红。

### 原先列出的两个待回答问题，现在有了答案

1. **R-13（git history）从缓存读还是从 workspace 读？** 02 §7.6 写的是 `git log base_commit`（只走祖先，本身安全）。若 R-13 从**缓存**读，那么把 workspace 的历史截断到 base 是安全的；若从 workspace 读，截断会连带删掉它需要的祖先。
2. **Docker 沙箱挂载的是哪个目录？** 03 §13 只规定了容器的安全参数，没说挂载范围。生产环境里 agent 的工具集（`read_file`/`search_code`/…）都跑不了 `git log --all`——能跑的只有 `run_tests` 里的仓库代码，而它在容器内。所以真正的边界是"容器能看到什么"：
   - **worktree 模式**：gitdir 在 `<cache>/worktrees/<name>`，**在 workspace 之外**。只要沙箱只挂 workspace，容器里 `git log --all` 就没有对象库可用，泄露不成立。
   - **copy 模式**：gitdir 就在 workspace 里，对象与 refs 全在里面。挂载 workspace 等于把答案递进去——**这个模式下泄露在真实部署中依然成立**。

**已按下列默认实施**（2026-10-08）：

1. **R-13 只从缓存读历史**，workspace 只作为代码与运行测试的载体。这条是下面所有做法成立的前提，R-13 实施时必须遵守——若改成从 workspace 读，截断会把祖先一起删掉。
2. **copy 模式已截断**：checkout 到 base 之后执行 `remote remove origin` → 删除全部 ref → `reflog expire --expire=now --all` → `gc --prune=now`。只删引用不够（`git cat-file --batch-all-objects` 仍能列出对象），所以要真的 prune。base 的祖先全部保留。实测修复后：`git log --all` 只剩 base、`git show <fix>` 返回 128、fix 对象已不在对象库里，而 base 祖先完整、`git status` 正常。
3. **worktree 模式本地修不掉**：它与缓存共享对象库和全部 refs，从 workspace 里就能看到缓存的引用。它的隔离**依赖沙箱只挂载 workspace**——缓存（`<cache>/worktrees/<name>` 指向的 gitdir）在 workspace 之外，容器里没有对象库可用，`git log --all` 会直接失败。

   ⚠️ **这是 E 簇沙箱实现时必须遵守的硬性约束**：沙箱只能挂载 `workspace.path`，**不得**把 `cache_root` 或整个 `runs/` 目录挂进去。挂载范围一旦放宽，03 §11.2 的隔离就失效。
4. **已加断言**：`test_worktree_gitdir_lives_outside_the_workspace` 钉住第 3 条依赖的前提（`.git` 是指向 gitdir 的文件、且 gitdir 在 workspace 之外）。若有人改动 worktree 创建方式让 gitdir 落进 workspace 内部，这条会变红。copy / fetch 模式的断言见 `test_self_contained_workspace_has_no_commits_after_base`。

**在 E 簇沙箱落地并验证挂载范围之前，不得给出任何 resolve 率数字。** 理由从"这个泄露还没修"改成"沙箱尚未实现"——沙箱是 02 §13 规定的隔离边界的执行者，边界没落地就等于没有。
